# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"The Iceberg of Magic" — a NeoForge mod for Minecraft **1.21.4** (NeoForge 21.4.157, Java 21). Mod id: `magical`, base package `com.efkrdnz.magical`. Design intent in `Iceberg_of_Magic_Design_Document.md` (tiered magic: Arcane → Elemental → hidden Authority endgame) and `SKILL_CREATION_NOTES.md` (visual contract: no reused vanilla projectiles, custom renderers + shaders).

## Commands

```powershell
.\gradlew build                      # compile + assemble mod jar
.\gradlew runClient                  # dev Minecraft client
.\gradlew runClient -PquickPlay="New World" -PautoScreenshot=200   # join a world at launch; screenshot 200 ticks in
.\gradlew runClient -PquickPlay="New World" -PautoScreenshot=300 -PautoCommands="magical unlockall;magical hud equip 1 gabriel" -PautoHold=cast_slot_2   # ... after commands at tick 40, holding X for the last 60 ticks
.\gradlew runClient -PquickPlay="New World" -PautoCommands="magical hud rule gravity increase_gravity;100:magical hud rule velocity stop" -PautoScreenshot=52,112 -PautoExit   # commands at ticks 40 and 100, a capture at each, then the game closes itself
.\gradlew runServer                  # dev dedicated server (--nogui)
.\gradlew runData                    # run data generators → src/generated/resources/
.\gradlew runGameTestServer          # run registered gametests headlessly
.\gradlew test                       # JUnit 5 unit tests
.\gradlew test --tests "com.efkrdnz.magical.SomeTest"  # single test class
```

- On macOS/Linux use `./gradlew`; Gradle 9.2 needs a JDK ≤ 25 as `JAVA_HOME` (the Java 21 toolchain is auto-provisioned).
- `src/main/templates/META-INF/neoforge.mods.toml` is a template; `${mod_id}` etc. are expanded from `gradle.properties`. Edit template + `gradle.properties`, never generated `mods.toml`.
- `src/generated/resources/` is a resources source dir alongside `src/main/resources/`. Datagen output.

## Architecture

### Entry point & registration

`MagicalMod.java` (`@Mod("magical")`) wires all `DeferredRegister` holders from `registry/` onto the mod bus. Each registry class follows the same pattern:
- `registry/MagicalBlocks.java` — `DeferredRegister.Blocks`
- `registry/MagicalItems.java` — `DeferredRegister.Items` (all `BlockItem`s)
- `registry/MagicalEntities.java` — ~40 entities, almost all `MobCategory.MISC`, invisible gameplay entities
- `registry/MagicalMenus.java`, `registry/MagicalAttachments.java`, `registry/MagicalCommands.java`, `registry/MagicalChunkTickets.java`, `registry/MagicalCreativeTabs.java`, `registry/MagicalBlockEntities.java`

Game-bus handlers are `@EventBusSubscriber(modid = MODID)` annotated classes — never manual `NeoForge.EVENT_BUS.register`.

### Three magic systems

1. **Arcane (Tier 1, composable spell-crafting)** — `arcane/` package. Runes + shapes + modifiers defined in `ArcaneContent`, resolved by `ArcaneSpellResolver`, cast via `ArcaneCastingService`. Has its own `AttachmentType` (`ARCANE_DATA`), own sync payload (`ArcanePlayerDataPayload`), own client mirror (`ClientArcaneState`). Separate from `magic/`.

2. **Elemental skill-based (Tiers 0-5)** — `magic/` package. ~80+ skills defined as `MagicSkillDefinition` records in `MagicContent` (static `register(...)` calls with base stats). Skills classified into sets controlling random unlocks/GUI: `SUB_SKILLS`, `AUTHORITY_SKILLS`, `CLASS_REWARD_SKILLS`, `CREATED_SKILLS`. Negative `tier` values mean hidden/authority content, excluded from random rewards.

3. **Authority (hidden endgame)** — `magic/AuthorityContent.java` defines endgame unlocks (Space, Soul, Chronos). Gated behind the Authority dimension progression. Skills like `CREATE_SUBSPACE`, `MANIPULATE_SPACE`, `POCKET_DIMENSION`, `SOUL_VOW`.

### Cast flow (keybind → render)

1. **Client tick** — `MagicalClientEvents.Hud.onClientTick` polls `MagicalKeyMappings` (Z/X/C/V = 4 loadout slots, B = loadout switcher / counter answer, K = codex, R = barrier refill). Hold/charge skills (Barrage, Subspace, Aegis, Black Flames, etc.) are intercepted by per-skill input handlers (`MagicBarrageInput`, `SpaceAuthorityInput`, `SovereignAegisInput`, etc.) before normal cast. Normal press sends a `CastLoadoutSlotPayload`.

2. **Server dispatch** — `MagicalNetwork` routes payloads. `MagicCastingService.castResolved` checks cooldown/unlock/mana, then routes via an **`if`-ladder** (special skills first: Vault of Avarice, Subspace, Space Walker, Aegis, etc.), then a `switch` on `MagicSkillType` (`PROJECTILE`/`BURST`/`BARRIER`). That `if`-ladder is the real routing table — every skill with custom behavior has an explicit ID check.

3. **Entity + renderer** — Service spawns a custom entity from `MagicalEntities`. The renderer (bound in `MagicalClientEvents.registerRenderers`) draws it using custom quads/beams/rings via `MagicalRenderTypes`.

### Player data & sync

- Two `AttachmentType`s, both `.copyOnDeath()`, registered in `MagicalAttachments`: `MAGIC_STATE` (`PlayerMagicState`) and `ARCANE_DATA` (`ArcanePlayerData`).
- Sync is copy-based and wholesale: `state.sync(player)` → `PlayerMagicStatePayload` → client; `MagicalNetwork.syncArcaneData(player, data)` → `ArcanePlayerDataPayload`.
- Static client singletons (`ClientMagicState`, `ClientArcaneState`) replace their contents on payload receipt.
- Side safety: `MagicalNetwork.handleClientPayload` uses `FMLEnvironment.dist.isClient()` + reflection into `client/ClientPayloadHandlers` — server never classloads client code.

### Network

All payload records in `network/` (24 payloads). `MagicalNetwork` registers them in `registerPayloads` using `event.registrar("1")`. Play-to-client: state sync, first-person effects, counter prompts. Play-to-server: cast requests, hold/charge state, wheel casts, class actions, space rule applications.

### Classes

`classes/MagicalClasses.java` — 16 classes (Blacksmith → Divinesmith, Warrior → Berserker/Warden, etc.) as `MagicalClassDefinition` records with parent class, XP cost, granted skill IDs. Tree-based progression tracked in `MagicalClassProgress`. `PlayerMagicState.evolveClass` validates prerequisites and grants skills.

### Passives & curses

`magic/MagicPassiveContent.java` — 8 normal passives (Mana Skin, Heat/Poison/Magic Resistance, Mana Flight, etc.) + 7 sin passives + 7 curses + 1 mana leak curse. Normal passives have a disable checkbox. Curses have no checkbox — require a Dispel action with conditions. Passives appear in a separate tab in the Magic Codex.

### Space authority laws

Manipulate Space writes one law per category onto the caster's `SpaceSubspaceEntity`, whose tick runs all twelve over everything inside the radius. **A law has two halves and they run on different machines** (`magic/SpaceLawPass`): the server carries the *consequences* — damage, effects, air, the flight Control Gravity hands out, the body a boundary moves — and each *client* carries the *movement*, against its own player and nobody else's (`client/SpaceLawClient`, on `PlayerTickEvent.Pre`, so a law sets the velocity the player's input then works against). The server never writes a player's velocity because it cannot deliver one: vanilla sends the `hasImpulse` motion packet over `broadcast`, and `ChunkMap.TrackedEntity.updatePlayer` never puts a player in its own audience; the one channel that would reach them, `hurtMarked`, replaces the client's velocity with the server's copy, and nothing in `handleMovePlayer` ever writes a real one. So a law aimed at Everything or Players used to move mobs and do nothing at all to a player — every law except Control Gravity, which works only because abilities have their own packet. Adding a law means threading `SpaceLawPass` through it and putting the `setDeltaMovement` behind `pass.moves()`; `SpaceLawGameTests` fails the moment the server starts pushing players again. Captures: `/magical subspace create [radius] [follow]` raises a domain with none of the skill's gates and `/magical subspace rule <category> <operation> [target]` writes a law onto it (defaulting to `everything`), so one launch drives the real rule loop: `.\gradlew runClient -PquickPlay="New World" -PautoCommands="magical subspace create 8 true;60:magical subspace rule gravity remove_gravity everything" -PautoScreenshot=70,100 -PautoExit`. `/magical hud rule` is a different thing — only the flash, no subspace.

**The boundary** (`client/renderer/SpaceSubspaceRenderer`, geometry in `client/renderer/space/SubspaceVault`, optics in `SubspaceOptics`) is a **vault**, and the whole of it is a reaction to where the camera stands. A domain is a sphere pinned to its caster body centre (`DomainEntity` sets `owner.getY() + bbHeight*0.5`) while the camera is at their eyes, so the eye sits **0.72 blocks above the centre and nowhere else** - the horizontal offset is exactly zero - and two things follow that the dome before this fell foul of. **First, every sight line runs along the surface normal**, to within 1.43 degrees at radius 16, so the inverted Fresnel that wall was built on varied by `5.3e-10` of alpha across the entire visible sphere: a dither of 1/510 was three million times larger, and the only spatial structure on the wall was the noise. It was a flat 7% that moved a daylight sky by 15 levels and blackstone by **2 of 255**, and four green tests certified it, because every one of them measured the mean alpha over the projected disc - a property of a viewer standing *outside*, which is a viewer who cannot exist, because a domain discards itself when its owner leaves it. **Second, every meridian plane contains that eye**, and a planar curve seen from a point in its own plane projects to an exactly straight line - not nearly, exactly, at every radius and bearing. So a member drawn up a meridian is drawn as a ruler, and a straight near-vertical bar at twenty blocks is a tree trunk, a fence post or a portal jamb.

So visibility is not carried by shading at all, and the structure is not a graticule. The pane is `A_PANE` = **3%**, half what it was, a tint that carries no reading; everything legible is a **chamfer** - a lip darkening toward `BODY` meeting a lip lightening toward `GLAZE` at a one-pixel arris. The two move a background in opposite directions, so whichever lip the background defeats the other one carries, and the worst case over every background in the game has a closed form, `A_SHADOW*A_HIGHLIGHT*(GLAZE-BODY)/(A_SHADOW+A_HIGHLIGHT)` = **57 levels of 255**, which is `SubspaceOptics.chamferFloor` and is pinned by `SubspaceVaultTest.theWallCannotBeInvisible` - the test the old wall got 2 on. The arris is measured in the same `fwidth` the stroke is, so at grazing incidence both blow up together and the chamfer can never flatten into one mid-blue line. The Fresnel is kept on exactly one branch, the outside one, where `b/R` genuinely sweeps the disc and the limb genuinely is where a silhouette lives; the caster branch is fenced between two named comments and `SubspaceShaderAssetsTest.theInsideMembraneHasNoViewAngle` fails if `dot(`, `viewDir` or `shellNormal` ever appears between them.

The object: a **springing course** right round the wall, twelve **ribs** climbing from it to an open **oculus** at latitude 78 where the pane is cut away entirely, and a **plinth** tracing where the wall meets the floor. **The ribs are wound**, `bearing = 30k + twist*(latitude - springing)`, and `twist = TWIST_BASE + TWIST_PER_LAW * lawCount` - so a rib leans 23 degrees off vertical with nothing written and 52 with all twelve, and **how much law is in force is legible from the silhouette** before a glyph is parsed. That single constant answers three things at once: it takes the ribs off their meridians so they are not bars, it destroys the lat/long generator so the wall is not a wireframe globe, and it makes the shape a function of the contents. Slot *k* is `SpaceRuleCategory.values()[k]` and owns bearing 30k for good, gravity due north, so **twelve ribs wrap the whole horizon** and `floor(102.4/30) = 3` of them are in frame from every bearing there is - the reading the old band failed hardest, with all twelve marks on one arc round north and under 0.3% of the frame from three quarters of all directions. A written law makes its rib heavier (`RIB_LIT_GAIN`), colours both lips with `HudPalette.change`, lights a **notch** on the course and hangs a **boss** carrying its `SpaceRuleChange` glyph; an unwritten one is held back to `NOTCH_DIM` instead of left out, so the count has a denominator. Gravity reads twice: level is one course, inverted winds the domain the other way and lights every member from beneath, dissolved breaks the course and the plinth into dashes. Nothing has a clock - `GameTime` is forbidden in all three shader files and a test enforces it - and the only motion is three CPU one-shots: a rib climbing once as its law is written, a ring running out from a crossing, the wall fading up over 12 ticks. The springing course is placed at a constant **apparent elevation** (14 degrees) rather than a latitude, because a fixed latitude sinks underground as the radius grows; the aiming line and everything within 4 degrees of it is clear pane, which `SubspaceVaultTest.theAimingLineIsClear` holds at every radius the skill can raise.

Captures: a domain ends when its caster leaves it, so **the outside case cannot be photographed in single player** and lives in the optics test instead. Laws written at `everything` physically shove the caster off the centre of their own dome and every frame is then shot off-axis - use `everything_except_user`. The target names are `everything_except_user`, `everything`, `living_entities`, `projectiles`, `players`; there is no `mobs`. The dev world persists between runs so the stage is absolute, and `forceload add` plus twenty ticks is needed before any `fill`, or the commands run on unloaded chunks. ### Chaos authority: the Pile and the Fracture

Layer -6 with the other authorities, and the one that owns no region, no entity and no grammar. **Chaos owns a Pile in the world and a Fracture in the hand.** The Pile (`magic/chaos/Pile`) is a sparse map of *sites* to one integer of **stress**; a site is a block position or a living body (`PileSite`), its **capacity** is decided by what it is and never by who owns it (`ChaosCapacity`: stone-like 4, dirt/sand/wood 2 - named by `BlockTags` rather than measured, because cobblestone and planks are both hardness 2.0 and stone is 1.5 - glass and leaves 1, unbreakable 8, a body 2 + armour/5, a player 3, **another Authority's construct 1**, which is the counter ring expressed as a physical property). A site holding more than its capacity **gives way** into its neighbours, and a neighbour that was already full gives way in turn. The wielder is a site like anything else: there is no except-the-caster clause, because the Pile is matter and matter does not know who made it.

**There is no random number in the whole Authority.** Self-organized criticality is the canonical model of a system that is completely deterministic and completely unpredictable, which is the actual definition of chaos, so the unpredictability is a property of the arithmetic. It is also why the core is pure: `Pile`, `Fracture`, `Fault`, `PileSite` and the `PileWorld` interface have no Minecraft in them at all and `PileTest` pins every rule on an exact value. `LevelPileWorld` is the only class that knows about a level, and it answers in a **stable order** - `Direction.values()` for blocks, entity id for bodies - because ties in a sandpile are broken by neighbour order and a cascade that reshuffled its neighbours would stop being deterministic.

The **Fracture** (`Fracture`, on `PlayerMagicState`, saved as a `ListTag` of five `Fault` names) is the customizable toolkit: five faults in an order, generation *n* of a cascade giving way by fault *n* and anything deeper keeping the last. So a collapse **changes character as it grows**, along a curve its owner authored - *SLUMP → SLUMP → HEAP → SHED* is a landslide that gathers, converges and detonates. The seven faults are SLUMP (all of it to the lowest neighbour), HEAP (to whichever already holds most), BLOOM (split evenly), HUNT (only to living neighbours), RECOIL (back the way it came), SHED (passes nothing on, spends it as force and harm where it stands) and ROOT (keeps it and raises its own capacity, swallowing the cascade). Seven across five positions is 16807 machines, carried on the wielder, available the day the Authority is taken.

**Entropy is the one law that knows which way time runs, so there is no CLEAR and no RESTORE**: nothing removes stress from a site. It leaves by exactly two routes - the site gives way, or the site is forgotten. The same rule settles preparation-as-a-weapon: a site that has given way goes **slack** for `Pile.SLACK_TICKS` (600) and refuses further stress, so ground you have already avalanched is dead ground and an hour of seeding cannot be re-used on the next opponent. A slack site may still *receive*, which is how RECOIL sends a cascade back into the ground it came out of without looping forever.

Four skills, three of which carry no numbers at all (`MagicCastContentKept`, `ChaosAuthorityService`): **Burden** (2 mana, 4 tick cooldown, one unit onto whatever the crosshair is on, sneak for yourself, and it is meant to be pressed dozens of times), **The Fracture** (a hold overlay, 100 tick cooldown so it cannot be re-cut inside a cascade), **The Last Grain** (4 mana, one more unit from nowhere - on ground below capacity it is a click and nothing else, and that is the skill), and **Criticality** (72 mana, 1200 tick cooldown, every capacity in the Pile drops by one for 200 ticks so everything standing lets go at once; on virgin ground it is an expensive shimmer). Their magnitude cannot be balanced by numbers because their magnitude is the work behind them.

`PileService` holds one Pile per wielder, keyed by UUID, and **it is never saved**: stress is dropped on logout and rebuilt from nothing on a change of dimension. That is thermodynamically apt and it settles griefing, the save format and unbounded growth in one decision - the kit the player authored survives, the battlefield does not. It runs the avalanche on `ServerTickEvent.Post` with a per-tick budget (`Pile.DEFAULT_BUDGET` = 48) so a long cascade visibly rolls over a second or two instead of resolving inside one frame, paints stress as `ParticleTypes.WITCH` motes every 10 ticks (**visible to everyone**, which is the whole of the counterplay: break the block it sits on, hit the body carrying it, deny the ground) and puts an `n/cap` readout on the actionbar for the aimed site. A proper crosshair pip belongs on a HUD layer through `HudBatch` and would move `HudSnapshotBudgetTest`; deferred.

### Authority of Causality: the board and the ledger

Layer -6 with the other authorities, and the one nobody presses. Every other Authority is a key held down - Chaos burdens, Mana recites, Space writes a law - and this one is a machine that runs while the wielder is doing something else: the work happens at the **board**, hours before the fight, and what is spent in the fight is having been right. Five skills and four of them are a single press (`MagicContent`, `MagicCastContentKept`, all `selfManaged`): **Causal Board** opens the wall, **Causal Anchor** puts a Mark on what the crosshair is on (`Anchor`, 900 ticks, 28 blocks), **Decree** is the one cause fired by hand, **Recompense** drains the whole ledger into one body as magic damage, and **Suspend** turns the board off without unpicking it.

**The shape is a directed graph, because the other three are not.** A `Weave` is up to 24 pins and 32 pieces of string on a 320x180 board; `NodeKind.mayFeed` is the entire grammar (cause 0, condition 1, effect 2 - never backwards, never into a cause, never out of an effect) and `Weave.connect` refuses a loop by reachability, returning a named `WireRefusal` (`NOTHING_THERE`, `WRONG_WAY`, `TOO_MANY`, `ALREADY`, `LOOP`) so the screen can say which rule was broken rather than failing silently. NBT stores enum **names**, so reordering a vocabulary can never turn an Erase into a Store, and a load runs its wires back through `connect()`, so a hand-forged save cannot inject a loop the editor would refuse.

**Conservation is the whole of the balance, and it is the reason the Authority rewards engineering rather than rewriting.** Paradox is charged for breaking conservation and never for moving it: `RETURN` and `PASS` send a consequence somewhere else for 0.08 a point, `ECHO` invents one for 0.5, `SEVER` for 0.6 and `ERASE` unmakes one for 0.9, while `STORE`, `SPEND`, `MEND` and `WARD` - which only move a number between the world and the ledger - cost nothing at all. The price is charged on the **scaled** amount, so `LESSER` genuinely is the cheap way to do a thing and `GREATER` genuinely is not. That rule had a hole in it that no test caught until `ERASE` was made to report what it unmade: `Weaver.commit` returned zero for it, so it was billed the flat `PARADOX_FLOOR` instead, which made erasing a big hit **cheaper per point** than erasing a small one - the central price of the Authority, exactly inverted. `WeaverTest` pins it on exact values now.

Paradox has three rungs (`Paradox`): Settled, **Strained** at 40 (every action costs double mana), **Fraying** at 70 (any chain longer than `FRAYING_DEPTH` = 3 pins is cut and everything that still fires is halved - so fraying takes the elaborate machinery away first and leaves the canonical `cause -> question -> consequence` working), and a **collapse** at 100, which shuts the board for `COLLAPSE_TICKS` and pays the ledger out of the wielder's own hide.

**The core is pure.** `Weave`, `Weaver`, `Ledger`, `Paradox`, `CausalNode`, `CausalEvent`, `WeaveReview` and the `CausalWorld` interface have no Minecraft in them and are pinned on exact numbers; `LevelCausalWorld` is the only class that knows what a level is. Same split as `Pile`/`PileService`, for the same reason.

Three things in the runtime are not obvious and all three are load-bearing. **The splice**: `CausalityEvents.hurt` has to run *before* `state.absorbDamage` or banking a hit would not save the barrier, and `broke` has to run *after* it, and a standalone `@SubscribeEvent` cannot promise its rung on the damage ladder - so both are spliced inline into `MagicGameplayEvents.onIncomingDamage`, and `CausalityGameTests.aStoreRunsBeforeTheBarrierAndNotAfterIt` is the only thing in the project that checks it. **Re-entrancy**: `BRIM` is fired by the server tick one tick *behind* the Store that fed it and never inside the dispatch, so the commonest board there is - bank a hit, spend it at 20 - never re-enters the engine at all; `MAX_CASCADE` = 3 and `CASCADE_PARADOX` guard the genuine recursion, and `noteLedger` only ever lowers its watermark, so a Store made inside a dispatch still reads as a rise on the next tick. **Billing**: mana and ledger are taken at resolve time for *every* action including a delayed one - only the landing waits - so a Delayed Spend cannot draw against a ledger that has moved on since.

Reaching outside yourself is the doc's progression and it is written in the weights: your own causality weighs 1, the three `MARKED_*` causes weigh 3 and refuse to fire without a Mark, and `Scope.FIELD` weighs 4. `WeaveReview` is as load-bearing as the engine, because every way a graph can be quietly wrong is invisible at runtime - `ORPHANED`, `DANGLING`, `NOTHING_TO_REWRITE` (a rewriting effect on a cause whose event is already over), `NEVER_TRUE`, `WANTS_MARK`, `TOO_DEEP` - and the board prints the first of them under the reading.

**The screen** (`client/screen/causality/CausalBoardScreen`, geometry in `CausalBoardLayout`, pinned by `CausalBoardLayoutTest`) is frameless the way the Grimoire and the Manipulate Space selector are: one scrim over the world, every string carrying vanilla's drop shadow, `HudQuiet` standing the mod's own HUD down and `HudDebug.Captured` keeping the screen up for a capture. String is drawn as a bowed run of one-pixel dots, each shadowed one pixel down and right, which is what lets a *line* sit on daylight terrain at all - it gets the same contrast a letter gets, so the scrim never has to be heavier than the Grimoire's. The board keeps a **uniform scale**, so a wall built on a wide screen reopens on a narrow one as the same drawing rather than a squashed one. **The knot is tied after a pin's name, not at its glyph**: a name is drawn to the right of its glyph, which is exactly the ground the outgoing string has to cross, so tying it at the glyph painted the label over its own run and a chain read as unconnected at precisely the pin that connected it - `theStringLeavingAPinClearsThePinOwnName` holds it now. 54 distinct 9x9 glyphs in `CausalGlyphs`, held apart by `CausalGlyphsTest`.

**The Mark is chosen, not taken.** Causal Anchor is a hold (`client/CausalAnchorOverlay`, geometry in `client/CausalAnchorLayout` pinned by `CausalAnchorLayoutTest`, driven by `client/CausalityAuthorityInput` the way `ChaosAuthorityInput` drives the Fracture), because the Mark is the dearest thing on the board - three causes weigh 3 apiece for it and two conditions are dead without it - and taking it off whatever sat under the crosshair at the instant of a keypress was the one press in the Authority you could least afford to fumble. Hold the key and every living body within `Anchor.REACH` gets a ring; scroll or the mouse buttons walk the focus; release marks it. **Three readings on three channels that cannot be confused** (the rule the loadout switcher settled): *where* a body is, is the ring drawn on it in the world; *which* one is focused, is its place on a rail of pips plus the ring's **shape**, solid against dashed; *what it costs you* is the words, which are the only thing the world cannot say - whether it already wears the Mark, and **how many pins on your board are asleep for want of one** (`WeaveReview.Kind.WANTS_MARK`, so on a board with no marked pin the honest answer is none). The last line says up front when a release will be refused for cooldown, because a chooser that lets you weigh three bodies and then says no is worse than one that never opened. The list is re-gathered every tick and the focus is kept **by entity id rather than by index**, or two steps while you decide slides it onto whatever took that place; the focused body is exempt from the forward cone, so turning your head never drops what you had settled on.

`client/renderer/causality/AnchorMarkRenderer` draws the rings on `RenderLevelStageEvent.Stage.AFTER_CUTOUT_BLOCKS` through `MagicalFxRenderTypes.glyphInkThrough()` - **through terrain**, because a Mark reaches 28 blocks and the body worth marking is regularly the one behind the pillar. There is no projection arithmetic anywhere in it: the ring is a quad at the body with the camera rotation applied, so the game does the projecting and a mark cannot drift off its body when the field of view moves, which it does every time the wielder sprints. Two things about handing that shader a ring are not guessable and cost a silent blank frame each. **`phase` is a position in a glyph's life, not a reveal**: `rendertype_glyph_ink.fsh` reads 0..0.25 as inking on and 0.75..1 as burning away, so the innocent 1.0F means *finished* and `dissolve` erases every pixel - a mark that must sit still while a key is held lives at 0.5 and never moves. And **the shader strokes the middle of whatever annulus it is given**, with the width a fraction (`0.06 * 1.25^paramB`) of the band rather than of the radius - so a hairline `innerRatio` yields a hairline whatever the weight, and the ring is built from a wide band (`BAND_INNER`) with the outer radius divided by `BAND_MIDDLE` to put the drawn stroke back where it was asked for. Judge the colour at midnight, as with every additive effect in the mod; in daylight both ambers clip toward white, which is exactly why focus is carried by shape.

### Authority of Mind: illusions believed per viewer

Layer -6 with the other authorities. **Reality is consensus**, and stage 1 is the half of it where nothing becomes real: the wielder writes a scene, sets it down, and every mind that sees it decides for itself how much it is there. The shape is a **belief matrix**, viewer by element - which is why this Authority cannot be pressed at one target and why the same wall is solid to one husk and air to the next. Stage 2 makes a lie real by consensus and stage 3 puts the sure to sleep (both below).

**The Lexicon** (`magic/mind/Lexicon`, on `PlayerMagicState.mind()`, saved) is what can be imagined: gazes per impression (`block:<id>`, `creature:<id>`, never a player). `MindGazeService` counts a still look - 40 ticks a block, 60 a creature - as one gaze; fidelity is 1/2/3 at 1/5/20 gazes and is worth plausibility; the budget is `16 + 2 * impressions` elements, capped at 128. A wielder who has only looked at stone can only lie in stone. What is looked at is one function on both sides, `MindGazeService.lookedAt` (a collider clip to 16 blocks, then an entity sweep at 0.3 tolerance, armour stands excluded), so the eye `GazeEyeOverlay` fills on the client is the thing the server counts; the server alone decides what is learned. A look teaches nothing once an impression is fully learned (`FIDELITY_3_AT` gazes) or anywhere in the dream, and the eye does not open on it (`Lexicon.studyable`, which both sides ask).

**A reverie** (`Reverie`, three slots on `MindState`) is imagined blocks and figments at offsets from an anchor, in the facing it was written in. Face-connected blocks are a **cluster** and a cluster is one element: believed, sensed and shattered whole, carrying the union of its members' senses (`normaliseSenses`, run on every add and every load). Senses (Sound x1.25, Shadow x1.15, Scent x1.10) multiply the gain and cost 10 mana a layer. Figments carry a `Script` (stance: Idle, Wander, Guard, Follow; reaction: Ignore, Approach, Flee, Stare, Chase). A name is capped at 32 wherever it comes from.

**Plausibility** (`Plausibility`, pure, pinned by `PlausibilityTest`) starts at 0.5 and is moved by support, context within 8, alien material, fidelity, habitat, whether the script is like the kind, and size; `LiveScene` re-reads it every 100 ticks because the world around a lie changes, with one context scan per re-read shared by all its clusters (`Plausibility.surroundings`) - 17^3 blocks a cluster was half a million lookups for a scattered reverie. **Belief** (`Belief`): `b += 0.02 * p * senses * susceptibility * novelty * (1 - b)` while seen, -0.002 a tick while not, and contradiction is the only fast way down - touch -0.60, a projectile through it -0.35, watching someone else touch it -0.20, a figment's hollow strike -0.25. First-hand evidence on a viewer who holds no belief at all - a touch, a blow through a figment, a hollow strike - shatters the element outright (`Belief.expose`), or a wall walked through unseen would fade in the moment its viewer turned round; watching someone else still needs a belief to dent. Below 0.1 it **shatters** for that viewer, never to be seen again, and `Scepticism` halves their novelty for every impression in it for 6000 ticks (cleared with the scenes on server stop). The wielder's susceptibility is zero by construction: they are never a viewer.

**The runtime** (`MindService`, never saved) holds at most two `LiveScene`s per wielder for 1200 ticks. A touch is **edge-triggered** (`LiveScene.inside`): standing in a lie is one contradiction, not twenty a second, and a viewer inside a lie gains nothing on it. Imagined blocks are never placed: the server finds a body that walks into one by its box, and **mobs path by what they believe** through the mod's first mixin, `mixin/WalkNodeEvaluatorMixin` on `WalkNodeEvaluator.getPathType(PathfindingContext,int,int,int)` - BLOCKED for a believed imagined solid, WALKABLE for open air over a believed imagined floor, both at `Belief.PATHING` (0.3), vanilla otherwise, and one boolean (`MindService.anyLive`) when no lie stands anywhere. `defaultRequire: 1` makes a missed injection a load failure. A **figment** (`entity/mind/FigmentEntity`) is a real, tracked, non-saving `PathfinderMob` that is **no body to anything outside the Mind**: `canBeSeenAsEnemy` is false, so no vanilla aggressor (Wither, Zoglin, Warden) targets it; `FigmentEntity.isFigment` takes it out of the mod's own targeting (`AimResolver`, `SkillTargets`, the Causal Anchor chooser, `LevelCausalWorld.nearby`), or a spell would land on a thing its caster cannot see; and it blocks no building, is fire-immune, takes no effects and throws no splash, bubbles or fall dust, because every one of those is drawn for every client, believer or not. Only believers deal with it, through the Mind's own `BelievedHuntGoal` and `BelievedFleeGoal` (`MindMobEvents`: every mob in `FigmentHunts`, every fearer), which look through non-combat `TargetingConditions` because the combat ones ask `canBeSeenAsEnemy`. A CHASE keeps its viewer until that viewer's belief shatters, or the hollow strike could never land. Perception is taken off the figment's live box, not the offset it was written at, so a figment that has walked is seen where it is. A melee blow on a figment is refused and is a TOUCH; projectiles pass straight through it (`canBeHitByProjectile` false) and count as PROJECTILE; it discards itself the tick its scene is gone.

**Each client draws a lie as strongly as it believes it.** `MindSync` sends a scene to every player within 64 blocks and belief rows every 5 ticks - a viewer its own, the owner everybody's. `IllusionRenderer` draws imagined blocks through `renderSingleBlock` into `IllusionRenderTypes.block()` - the translucent shader with **colour write only and no depth write**, on the item-entity target, at `AFTER_TRANSLUCENT_BLOCKS` - and scales alpha (`Faded`, which must not override the bulk vertex paths, because their defaults route through `setColor`), at `min(1, b / 0.5)`. Both halves of that type are load-bearing: a depth-writing lie drawn at `AFTER_CUTOUT_BLOCKS` hid every mob behind it and was erased outright under Fabulous graphics. Only `RenderShape.MODEL` blocks are drawn. The owner sees 45% blocks with lilac edges and a lilac box round each of their own figments, or a wielder could not tell their lie from a real cat. A figment is drawn by a posed dummy of its kind (`FigmentDummies`, evicted when the figment leaves the level) once visibility reaches 0.5, and is pickable only then. **Belief Sight** (`BeliefSightRenderer`, at `AFTER_CUTOUT_BLOCKS` through terrain, sharing `AnchorMarkRenderer.band`) is one ring over each viewer: dashed lilac while doubting with opacity `0.35 + 0.6b`, solid gold once convinced, nothing once they have seen through every element.

### Sword school: the stances

A hidden chain of four found by the **Answering** (`magic/sword/SwordRiteService`: four swords shift-dropped at night under open sky, spread out and at rest around you, which go into the rack and stand up as the first formation; no command, no structure, no advancement, and `SwordRiteGameTests` is the only thing that says the class is reachable at all). Each rung flips exactly one rule and the whole kit is denominated in **a count of swords you can see orbiting your own head**: Summoner four, Rider seven and `worldOrigin`, Saint ten and every stance open, God twelve and `relentless` (every clock halved). There used to be a lattice - bearings you authored by standing somewhere and pointing, with one conserved divisible measure of Edge partitioned across them and a draw to bill it against - and it is gone entirely, because none of it was legible: a wielder looking at `24/84` on the HUD could not tell you what either number was. `SwordRules` is the rung, `SwordMath` is every damage number the kit has and its only input is that count.

**A stance is where the swords sit, which way they point, and what they do while your hands are busy**, and it is the whole of the design. `magic/sword/stance/` is **pure** - `SwordStance`, `Formation`, `Pattern`, `Slot`, `Watch` have no Minecraft in them, same split as `Pile`/`PileService` and `Weave`/`LevelCausalWorld` - so `FormationTest` pins all six at every complement, phase and look elevation on exact values, and it found three real defects doing it. Six stances: Guard (over the shoulders, points where you look), Vanguard (a cluster at eye level, `Anchor.LOOK`, rigid to the aim), Crown (a ring overhead, points out), Wings (swept fans at the shoulders), Coil (a level orbit at the waist), Rain (a scattered disc high overhead, points straight down). `SwordRules.stances` is a count taken **off the front of the enum's declaration order**, so reordering that enum silently moves which rung owns which stance - stated on both classes. **Nothing about a formation is on the wire**: the entity carries the stance, the present mask and the frame, and both sides run the same `Formation.place`. `Slot`'s axes are Minecraft's - **+X is the wielder's left**, because `calculateViewVector` turns yaw clockwise from above - and a sign mistaken there is a silent mirror: the formation appears on the wrong side for everybody at once, consistently, green build, nothing logged. `Formation.BODY_CLEARANCE` is **0.80** and the binding reason is that a blade is drawn about its own middle: the model is 1.26 blocks pommel to point, so half of it hangs back toward the origin and a slot nearer than that puts its own pommel in the wielder's chest. `SwordSilhouetteTest` measures the drawn half-length against it and is the only thing holding the two in step, since the pure package cannot see the renderer. It was 0.55, which was under the half-length *and* under the real floor - the tightest slot any of the six asks for is Wings at 0.8806.

**`Watch` is the half the user asked for by name - swords doing things by themselves** - and it runs on `SwordArrayEntity.tick`, every tick, not on the slow tick: an arrow has to be turned *before* it lands and ten ticks is eight blocks of arrow, and that entity exists only while the steel is out, so a sheathed wielder pays nothing. Three of the six spend a sword and three do not, and that is the balance stated once. Two things about Guard are load-bearing. Its projectile half is **gated by no passive at all** - Guard is a Summoner stance and the rung's whole clause is that the swords act on their own, so gating the one thing Guard does behind a Rider passive left the base rung's headline stance doing nothing; Ward of the Array buys the *other* half, a melee blow discounted, which lives in `SwordPassives.incomingDamage` because a blow can only be answered inside the damage event. And **Mirror of the Array** (the apex rung, which grants no active) is now the stance you were *last* in still watching: its Watch runs alongside the current one at half rate on a clock of its own (`SwordService.mirrorStance`/`mirrorWatchDue`), which is the one thing in the kit that makes a stance change additive rather than a swap.

**A stance caps its own complement, and the swords it does not field do not exist.** The rung offers 4 / 7 / 10 / 12 and the shape takes as much of it as its silhouette can carry - Guard 6, Vanguard 5, Wings 8, Crown and Coil 10, Rain 12 - applied at exactly one choke point, `SwordArray.swords()` = `stance.swords(min(rules.swords(), racked))`, because the live mask, Sword Heart's pool, a volley, the HUD's denominator and the picker's diagram all have to agree and a second place that applied only the rung would be a count that is right until somebody stands in Guard. There is **no reserve**: the swords a stance does not field are not held back for Loose or One Blade and they do not widen the pool. Guard is the complaint that started it - twelve blades on 250 degrees of a 1.25-block arc sit 0.50 apart, barely over `Formation.MIN_SEPARATION`, and read as a thicket rather than a guard - and the answer generalised: the two stances a Summoner starts in stay tight for the whole game, so climbing the chain buys steel as well as verbs. `SwordStanceTest` holds the two rules that keep it fair - a cap is never below the complement of the rung that *opens* the stance, so a new posture never greets you with a downgrade, and some stance still reaches twelve, so `SwordMath.SWORD_HEART_CAP` and the 60-damage apex volley stay reachable rather than becoming numbers that live only in the source. The apex volley is now 25 (Vanguard) to 60 (Rain).

**The away mask is a debt, and a stance is a window onto it - never an edit of it.** `SwordService.awayMask` carries every sword that is out and `presentMask`/`away` read it through `liveMask`, which is the stance's own width. Both obvious shortcuts are wrong and both are silent. **Clamping** the count on a change of stance (the first thing `recompactAway` did) hands out six free swords for two keypresses: spend twelve in Rain, tap Guard, tap Rain. **Windowing the return machinery** strands steel: twelve spent in Rain then a step into Vanguard leaves five visible, the clock brings those five home, the window then reads zero and the other seven never come back on any route - not a clock, not a walk-over, not a recall. So `recompactAway` only pushes the holes back down to the bottom of the mask (the run is not always contiguous: a spend takes the lowest free slot and a return frees the lowest away one, so a volley plus one return leaves bits 1..11) and `returnSwords`/`returnOne` read the whole mask rather than the window. `StanceGameTests` holds both, and both go red on the old code with exactly those numbers.

**The formation lags, and only its rotation does.** `magic/sword/FrameEase` is pure: a half-life approach (`1 - 0.5^(dt/halfLife)`, so the rate is the same at 20 Hz, at 5 Hz and once a render frame, where a per-tick fraction would run in slow motion on a struggling server) and a wrap-aware difference, because a naive lerp from 179 to -179 travels 358 degrees the long way round and a wielder walking past due south watches twelve swords whip round them. The server keeps `followYaw`/`followPitch` on `Held` and advances them **once per tick** from `SwordArrayEntity.tick` - the ease is state, a reader that advanced it would turn the formation once per caller, and the tick number is the guard - and `frame()` returns that eased rotation with the **origin exact**, because a lagging centre would let the wielder walk out of the hole in the middle of their own formation and `Formation.BODY_CLEARANCE` would stop being true. The half-life is per stance: Vanguard 1.2 ticks, because it is drawn on the crosshair and lag there is a lie about where you are aiming; Rain 5.0, because it hangs eight feet up and should swing like something heavy. **Crown and Coil take none of the turn at all** (`SwordStance.Anchor.ORBIT`, `ArrayPose.nextYaw`): both spin on their own clock, and a ring that also swung round every time its wielder turned the camera was two rotations fighting, so an orbit takes the wielder's bearing once as it is called, keeps whatever bearing it was entered at, and only its pitch settles level over the half-life; `StanceGameTests.anOrbitTakesNoneOfItsWielderTurn` turns a wielder 90 degrees under Crown and fails the moment the ring follows. `SwordStanceTest` pins that every one is positive (`FrameEase` reads zero as a snap, which would switch the easing off without failing) and that none is still more than 20 degrees behind a second after a half turn. On the client, `SwordArrayEntity.facingAt`/`lastFacing` walk between the last two facings the server sent, exactly as vanilla walks a position between `xOld` and `x`; angles rather than the vector, because two facings far apart lerp through the middle of the sphere and normalising something near zero is a NaN that takes the whole formation off the screen for a frame.

**Two clocks.** The renderer took the wave phase from `state.age`, the entity's own age, while `SwordService.phase()` reads `level.getGameTime()` - and an age starts when the spawn packet lands, so the drawn ring and the ring that actually hits sat at different angles by a constant offset that was *different for every observer*. `SwordService.phase`'s own note already said an age would not do; the renderer was the one place using one. It is `entity.level().getGameTime() + partialTick` now.

Two skills carry the whole interface. **Call the Blade** is the switch: press once and the racked swords stand up in whatever stance you hold, press again and they are gone - no entity, nothing drawn, nothing intercepting, no drain. Calling is billed and cooled; **sheathing is free and uncooled and is never refused**, because a wielder who cannot afford to put their own swords away is a wielder stuck holding them. **Sword Stance** is the picker. Every skill in the kit is `selfManaged` or `holdGated`, and both return out of `MagicCastingService.castViaRegistry` before a stat, a point of mana or a clock - so every number on those definitions is decoration until `SwordService.payFor` is called by hand, exactly as in the Authority of Causality. The other four spend the count: **Loose** throws every present sword on the stance's own `Pattern`, **Below** sinks them and turns them upside down, **One Blade** fuses the lot into one edge as long as the steel that made it, **The Keel** takes the frame off the body and spends one sword as a board.

**The school draws steel and nothing else.** Every sword on screen is Duskfall through `SwordBladeRenderer` - the formation (`SwordArrayRenderer`), a flown blade, One Blade's greatsword and Below's risers (`client/renderer/fx/paint/custom/SwordPainters`, the only two custom painters the school registers) - with no aura, glint, thread, strain tint, cast circle, muzzle flash or first-person preset: all six profiles are `CircleAnchor.NONE` with `FirstPersonSpec.NONE`, and `SpellFx.release` sends no release cue for a NONE anchor. `SwordSteelOnlyTest` scans the drawing and hit files and fails if any of it comes back. The one thing added to the frame is the **impact wave**: every hit goes out through `magic/sword/SwordImpacts` as one `SwordImpactPayload` (point, struck face normal, radius, kind, struck block) and `client/fx/SwordImpactParticles` throws it as vanilla particles - a `POOF` ring running out across the struck surface, `CRIT` sparks back along the blade, crumbs of the struck block - with every number in the pure `ImpactWave` (`ImpactWaveTest`). Seven kinds: CUT (a blade into a body, at its entry point), CLANG (into stone, with crumbs), PARRY (Guard turning a shot), SHEAR (Crown or Coil through a body, plus vanilla's sweep crescent), THRUST (One Blade's point on the blast), TREMOR (crumbs hopping on the rim of Below's circle every `TREMOR_INTERVAL` ticks of the warning) and ERUPTION (dust pillars across the whole circle as it commits). A volley into one body rings once: a hit near one that rang in the last few ticks is an echo and throws its sparks without a ring (`ImpactWave.Ledger`). The particle setting is honoured by hand, because `createParticle` skips `LevelRenderer`'s gate: none at Minimal, every other one at Decreased, nothing past 32 blocks. Below's rise is drawn on **draw mode 2** (`BelowSkill.RISE_DRAW_MODE`), because the planted blades carry Below's id at draw mode 1 and would otherwise each paint the whole eruption again; where the risers stand and how high they come (`riseOffset`, `riseHeight`) is held inside the cylinder that catches by `BelowSilhouetteTest`. Every profile still declares its old `.impact(...)` triple though nothing fires it: `VisualProfiles.validate` wants a distinct victim overlay per school and palette, and without them the mod does not load. A wave lives `RING_LIFE` (9) ticks, so a capture shoots within a few ticks of the hit - and the dev client is live while it runs, so a mouse moved over the window turns the camera and spoils every frame after it.

**The picker** (`client/SwordStanceOverlay`, geometry in `client/SwordStanceLayout`, pinned by `SwordStanceLayoutTest`) is the mod's third frameless surface and it is a row of six cells - Manipulate Space is three scrolling columns and the Fracture is five gates, and one choice out of six is one row. Each cell draws **the real formation**, `Formation.place` flattened and scaled to its own extent, so the picture cannot drift from the arithmetic it is a picture of, with a dim cross at the frame origin for the wielder: without it Crown's ring and Coil's are the same ring at the same size, and the only thing that tells them apart is that one is above the cross and the other is around it. Three readings on three channels - **hue** for what is worn (gold, plus the word), **brightness** for what is focused (white, and a brighter diagram), and the description line under the row. Frameless means a **scrim** (0x8C, the number the loadout switcher settled: it takes noon sand to 7.23/5.44/4.71:1 in the right order, where unbacked ink is 1.45:1 and the highlight actually inverts), and the sigil layer stands down while it is open. **Nothing in the layout is a constant the screen has to be big enough for**: six 72px cells want 452 and `Window.calculateScale` guarantees only **320x240**, so the cell width, the diagram, the row's drop and the hint's place are all functions of the gui. Two real defects came out of writing that test - the last two stances were off the right of the screen at maximum gui scale, and at 480x270 the description landed on y 239 and the hint on y 240, two lines drawn on top of each other. `HINT_FROM_BOTTOM` is 52 rather than a comfortable 30 because **vanilla's own HUD is still drawn and this overlay is under it**: the hotbar, hearts and XP bar own everything from y 321 down on a 360-tall gui.

**The rack** (`magic/sword/rack/`: `SwordRack`, `SwordRackRules`, `SwordArms`, `ArmDamage`; the menu `magic/menu/SwordRackMenu`, the screen `client/screen/sword/SwordRackScreen`, its geometry in `SwordRackLayout` pinned by `SwordRackLayoutTest`) **is the swords**. Sneak as you press Call the Blade (or `/magical sword rack`) and twelve sockets stand on a ring round the name of the stance, and **only what is racked exists**: an empty socket is nothing - there is no plain steel - so one sword racked is one sword round the wielder, and an empty rack draws nothing (Call the Blade refuses before it bills and says where swords come from; a rack emptied while the steel is out sheathes it). The count is `SwordArray.swords()` = `stance.swords(min(rung, racked))`: `SwordArray.racked` is a 12-bit copy of the sockets holding a weapon this wielder may fly, taken by `SwordService.refreshRack` (the formation's own tick, the open menu's `broadcastChanges`, the slow tick through `refreshRung`, a command, a press) and riding the save as a fourth int, because the client counts the formation, the HUD ring and the picker's diagrams off the tag the server writes. **Sword *j* is the *j*-th racked socket** (`SwordArray.socketOf`), so a gap on the ring is never a gap round the wielder: the away mask, `Formation.place` and every blade's slot count swords, and `SwordArms.arm`, `arms` and `allArms` map a sword to its socket, so a weapon follows its own sword out of the formation, into a body and home again. A change of rack pushes the away debt back to the bottom of the mask (`recompactAway`) exactly as a change of stance does - moved, never forgiven. Gold rims are the weapons that fly, slate an open socket (empty, a sword the stance does not field, or a weapon waiting for Weapon God), dark a socket a higher rung opens: it can be emptied and never filled; the count line reads what flies over what is racked. The rack is its own attachment (`MagicalAttachments.SWORD_RACK`: saved with the registry provider because it holds real items, `copyOnDeath`, deep-copied), never a field of `PlayerMagicState`, so neither death nor `/magical reset` takes anybody's weapons; `SwordArms.rackedMask` asks `hasData` before it reads, because `refreshRung` runs for every player on login and `getData` would hand each of them an empty rack to carry in their save. It takes swords only (`SwordRackRules.isSword`: the catalogue's SWORD and GREATSWORD archetypes, then `SwordItem` or `ItemTags.SWORDS`) until the Sword God rung grants **Weapon God** (`MagicPassiveContent.WEAPON_GOD`), after which it takes any weapon - axes, maces, tridents, bows, every forged one. `SwordService.refreshRung` hands the passive to a Sword God who evolved before it existed, and asks `hasPassive` first, because `unlockPassive` also re-enables a disabled passive and would switch it back on every slow tick. The Answering racks the four swords it was offered before it draws them (`SwordRiteService.rackTheOffering`), or the rite would raise nothing.

**A sword hits for its weapon.** Every sword hit goes through one door, `SwordArms.strike` - a flying blade's wound, Below, One Blade, the stances' sweep - and the kit's numbers in `SwordMath` are written in units of one sword landing (`BLADE_BASE` = 5). `ArmDamage` replaces the unit with each weapon's own hit: `SwordArms.weaponHit` is its attack as its tooltip reads it (the wielder's base attack, one for a player, plus every main-hand `ATTACK_DAMAGE` modifier in vanilla's add, multiply-base, multiply-total order, clamped as the attribute clamps), then `ForgeStrikeMath.baseHit` if it was forged - exactly what a forged swing starts from - plus what `EnchantmentHelper.modifyDamage` adds against *this* body; the wound lands `amount * ArmDamage.mean(scales, swords)`, each scale that hit over `BLADE_BASE`, so one sword of a 230-attack weapon lands 230, a diamond sword 7, and a wound of many swords the sum of their weapons. It used to be flavour capped at 15%, which is how a 230 sword came to hit for six. Then, only if the hit landed (health fell or the body died - a wound the barrier ate sets nothing alight), the weapon's own effects run **once**: its enchantments' after-hit effects off the first enchanted arm, on a copy so nothing in the rack wears, with a direct `playerAttack` source because Fire Aspect and its kind ask for one; and each forged element in the wound rides it once through `ForgeRiderService`, rolled the way the forge's own slashes roll. `SwordArms.accent` colours the hit - the first forged element, else fire for Fire Aspect or Flame - and `SwordImpactPayload` carries it as three bytes (`writeMedium`, never an alpha); an accented echo trades one spark for its mote, so a racked volley costs what a plain one did (`ImpactWaveTest.aVolleyOfRackedBladesCostsWhatAPlainOneDid`) and the Tremor warning carries no weapon.

**Drawn**, `SwordArrayEntity` syncs twelve `ITEM_STACK` accessors, one a sword, written only when `ItemStack.matches` says an arm changed; a flying `SwordBladeEntity` carries its own; Below writes the sunk arms into its synced data and `SwordPainters.below` parses them once per tag. A sword whose arm arrives empty is not drawn at all. **A held formation is drawn off its wielder, not off the entity**: `SwordArrayRenderer` takes the origin off the wielder's interpolated position through `ArrayPose.heldOrigin` - the one formula the server places a HELD or RIDDEN frame with (`Bind.followsTheWielder`, `ArrayPoseTest`) - and translates the drawing by the difference, because the entity's position reaches the client in steps a round trip behind the client's own movement: drawn from it, a formation round a walking wielder stuttered and trailed, while one round a wielder turning on the spot, whose facing is walked between ticks, was smooth. A racked Duskfall is the real model and anything else is its flat GUI icon (`ItemDisplayContext.GUI`) at `ICON_SCALE`, **billboarded about its own long axis toward the eye** (`ForgeView.eye`): Guard is seen from behind, and a flat icon seen edge-on is a dark bar. `SwordSilhouetteTest.aRackedWeaponIsTheSizeOfTheSteelItReplacesAndStaysOutOfTheBody` holds the icon's reach under the blade's half-length, so `Formation.BODY_CLEARANCE` stays true of whatever is racked. ### Sin system

`magic/MagicSinService.java` — 7 deadly sins track player behavior (Pride from full-barrier casts, Wrath from taking damage, Greed from hoarding, Sloth from idling, etc.). ### Forged strikes (the blacksmith/divinesmith left click)

An attack press holding a `magical:forged_weapon` runs `ForgeComboService`/`ForgePayloadService` -> `ForgeStrikeEntity.spawn` -> synced data -> `client/renderer/ForgeStrikeRenderer.extractRenderState` -> `ForgeForms.render` -> one of eight geometry classes in `client/renderer/forge/` (seven share one `forgeEdge()` consumer; SLAM spans two render types and is handed the source, because `ForgeBuffers` forbids two live consumers on the shared buffer).

Seven of the eight are built from `ForgeRibbon`. An arc of blade is a **closed solid**, not a sheet: four faces per segment, a lens cross-section (`crossSection`) that is sharp at both lips and thickest on the spine, tapered along its length by `bladeProfile`, with `planar(plane, u, v, n)` putting the thickness on the one axis the plane does not span.

**A swing may lean; a thrown thing may not.** An arc has a belly and a belly points somewhere — fine for a swing, which is a thing done in a direction with the wielder standing at the middle of it, and wrong for the wave, where whichever direction gets picked is arbitrary *and* is not the direction the wave is travelling. The wave was drawn tipped up-right, then bowed belly-down, and both were the same mistake. So it is not an arc at all: `ForgeWaveFront` is a **surface of revolution about the aim** — `point(radius, depth, angle, across)` gives the angle no say in depth, so the middle leads, the rim trails, and the sheet is identical at every roll angle about the flight line. `WaveSilhouetteTest` pins exactly that, plus the sizing below. Rings bunch toward the rim (`RIM_BUNCH`) so the shader's cutting lip lands on a thin band and the front ends on an edge; `halo` is its rim glow, written there rather than borrowed from `sheath` because a sheath tapers to nothing at both ends of its arc and a ring has no ends — a seam would be an in-plane direction again. Its wake is short and tapers hard (`TRAIL_GAP`, `TRAIL_SHRINK`): the thrower stands *behind* a wave, so every trail copy is nearer the camera than the head and perspective alone draws it larger.

**A drawn form must sit on the volume that actually hits.** An arc is measured from the centre of its own circle, so a crescent built at radius R puts every one of its pixels R blocks from the strike and none of them on it — which is how the wave came to be a band hanging between 1.5 and 3 blocks off the flight path, rolled 40 degrees, claiming nearly four times the width it catches in. `WaveSilhouetteTest` measures the drawn sheet against `HitShapes.forFamily(WAVE).broadInflation(halfWidth, reach)` — `WaveShape` inflates the swept box by `halfWidth * 0.48` laterally and a flat `0.9` vertically, and its `hits` only rejects things behind the wave, so that box *is* the hit volume. The vertical `0.9` does not grow with the weapon, so `WaveGeometry.radius` is a `min`, not a fraction: a heavy divine blade would otherwise be drawn reaching half again as far up and down as it catches. The glow and the wake are deliberately outside the measurement: a glow is light, and a wake is where the blade has already been, which the swept box covers. `ForgeMotion` opens an arc along its own span (`opening`) or grows a thrown one out to its reach (`reaching`, and `reached` for the factor alone, so the wave's front and the ring of ornaments round its rim cannot drift apart) - both capped so the drawing never claims more than the hit shape. Three things then sit on top of the steel, and all three exist because of one complaint - a swing seen down the line of its own plane is close to a line, and a picture of nothing but smooth ribbons reads as fog:
- **`ForgeAura`** - the one call each form makes after its arc. It reads the viewer's position straight off the pose matrix (`ForgeView.eye`, the inverse applied to the camera-relative origin), so a form that lifts, tilts, rolls or fans its arc is accounted for without saying so.
- **`ForgeRibbon.sheath` / `lanceSheath`** - a camera-facing glow band along the blade's spine. Its v runs 0.5 at the centreline to 0 at both rims, so it is symmetric and the shader's cutting-lip term never fires on it. Drawn once per strike, not once per trail copy.
- **`ForgeSparks`** - debris off the cutting lip, hashed from the entity id so every client sees the same shower. Slim camera-facing streaks; `count` is the grade's.

`rendertype_forge_edge.fsh` is where a strike gets its colour. The render type blends **`ONE, ONE`** - the alpha channel is discarded outright - so the vertex alpha must be folded into rgb, exactly as `magic_common.glsl`'s `additiveOut` does; `CEILING` is set from the layer stack (two faces x four to six trail copies ~ 3.5x) so the hottest pixel lands near white and everything short of it keeps the element's hue. `core` is the one term with a hard boundary and is deliberately kept out of the noise.

The weapon's own numbers show: element owns colour and ornament (`ForgeElementAccent`), form owns the silhouette, temper and modifiers already move `halfWidth`/`reach` through `ForgeStrikeMath`, and **`ForgeWeaponLook`** adds the last two - grade scales emission 0.62..1.28 and spark count 3..18, quality scales blade breadth 0.86..1.18 - applied once in the renderer, off `state.alpha` and `state.halfWidth`, so all eight forms inherit them.

### Weapon item models

Every weapon in `forge/weapon/MagicalWeapons` ships three files under its own path -
`assets/magical/items/<path>.json`, `models/item/<path>.json`, `textures/item/<path>.png` - and
`MagicalWeaponsTest.everyWeaponHasItsThreeAssetFiles` checks all three exist. There is no datagen
for them; they are written by hand.

All of them are one flat quad on `minecraft:item/handheld` wearing a 16x16 icon, **except
Duskfall**, which is a real 130-cuboid Blockbench export (source project and previews at
`D:\bb\eclipse_reaver`, authored as a standalone 1.21.4 pack). Importing one of those is easy to
get wrong in ways that never fail a build, so `WeaponModelAssetsTest` pins the three that matter
for every weapon model at once. **The namespace**: an export carries its own pack namespace on
every texture reference, and a reference into a namespace this mod does not ship resolves to the
missing texture while the model loads perfectly - so `eclipse_reaver:item/eclipse_reaver` had to
become `magical:item/duskfall`, and that rename is the one thing the test caught. **The UV space**:
`texture_size` is a Blockbench field that vanilla does not read at all, so UVs are always 0..16 no
matter how many pixels the sheet has; an export that leaves them in texture pixels samples a
two-pixel corner across the whole sword and the parser accepts it, because any float is a valid UV.
**The bounds**: vanilla refuses an element outside -16..32 or a rotation that is not 0, +/-22.5 or
+/-45 on one axis, and that refusal is a load-time log line, not a test failure, so the weapon
simply has no model in the finished game.

The display transforms need retuning on import and the test cannot help, because nothing about them
is wrong in the abstract - they are wrong relative to this mod. A standalone pack tunes its hero
item to fill the frame; here the same numbers made a sword 31 model units tall (about twice a
vanilla blade) cover a third of the screen in first person. First person went 0.72 -> **0.42**,
which puts its on-screen footprint beside a netherite sword, and the GUI went 0.46 -> **0.55** with
the translation pulled back toward centre. The GUI scale has a hard ceiling: the slot is 16 units,
the blade rotated -35 degrees runs along the slot diagonal at 22.6, so 0.62 clips the tip and the
grip out of the slot and 0.55 is the last value that does not. Third person was left exactly as
authored; it was already right.

### Training dummy

`entity/TrainingDummyEntity` is a practice target that never runs down, and the numbers above its head are the whole of it. The meter is the pure `entity/DummyMeter` (`DummyMeterTest` on exact strings): each hit is read in `actuallyHurt`, after vanilla is done with it, off NeoForge's `DamageContainer` - `getOriginalDamage` is what was dealt, `getNewDamage` what was taken, and armour, enchantments, effects and absorption each name their share, with whatever is left over as `other` (the mod's own modifiers, negative when a hit was amplified). ### Visual conventions (from SKILL_CREATION_NOTES.md)

- No reused vanilla projectiles, fireballs, or particles as main identity - as the matter a spell is made of they are the rule (below).
- Invisible gameplay entities + custom quad/beam/ring renderers.
- Custom core shaders in `assets/magical/shaders/core/` (`.vsh`, `.fsh`, `.json`), registered via `RegisterShadersEvent` → `MagicalRenderTypes`.

### The matter layer (accents)

Light is shader, matter is particles. Every `VisualProfile` carries an `Accent` (`magic/visual/Accent`: the school's by default, `.accent(...)` to name another - `FROST` for an ice skill in the Water school, `EARTH` for the ground moving, and three that belong to no school, `FORGE`, `BREW` and `BLOOM`, for the class skills - `NONE` for the old all-shader look), and with an active one the generic cues split in two: `client/fx/TransientVisuals` draws a lighter shader pass and `client/fx/SpellAccents` throws the matter as real particles - vanilla's (`FLAME`, `SPLASH`, `SNOWFLAKE`, `END_ROD`, `REVERSE_PORTAL`, `DUST_PLUME`, crumbs of the struck block, `EXPLOSION` and a `POOF` ring on a heavy hit) and the mod's four tinted sprites (`registry/MagicalParticles`: `RUNE`, `SHARD`, `MOTE`, `WISP`, spawned as `particle/TintedParticleOptions`, drawn by `client/particle/TintedSpriteParticle`, art from `scripts/particle-sprites.py`, pale so the tint is the only hue; a sprite's `gravity` is vanilla's field, spent as `0.04 * gravity` a tick; a light sprite is lifted to `LIGHT_SPRITE_FLOOR` and a shard to `SHARD_FLOOR` whatever the palette asks, because the Void palette's motes drew as black specks, and a wisp is smoke and keeps its colour). It exists because a capture of the whole roster showed nearly every skill the same way: a white starburst `1.6 x flashSize` blocks across on every hit, a second glyph circle stamped over it, up to sixty additive motes pretending to be debris, and the caster's own cast circle filling half (at the feet) or all (at the eyes) of a first-person frame. Every factor that fixed it is in the pure `AccentPlan` (`AccentPlanTest`): the flash at 0.7 of `flashSize` for six ticks in the palette's `BASE` rather than its pale `BRIGHT`, no delivery stamp, no ground mark on a hit with no ground behind it and the one there is - and every stain a skill leaves with `SpellFx.decal` - at `MARK_SCALE` and `MARK_OPACITY`, and 30% of the old motes - **and only the ones that are light** (`FxKinds.Smoke.glint`: sparks, glints, embers), because smoke, ash and ink drawn additively are black cards over daylight and fragments, glyphs, mist and droplets are white dice. A hit on a body throws its matter off the side the viewer sees, at its middle height (`TransientVisuals.viewerFace`, `BODY_FACE_GAP`), where it used to come out of the middle of the body and never be seen. A zone sized in blocks rather than by the tier sends `SpellFx.zoneTickWithin`, so its ripple is the ground it hurts. Moving profile entities trail their accent's particles by themselves (`SpellAccents.tickTrails`, one pass over `entitiesForRendering` a client tick), so no projectile needs trail code. Everything goes through `ParticleEngine.createParticle` so speeds are exact, and the particle setting is asked by hand the way `SwordImpactParticles` asks it.

**The caster's own view is where almost every problem was**, because everything a cast sends starts at the caster: the release is sent from the hand, 0.8 of a block in front of the eyes, and the circle from under the feet or 1.35 blocks ahead of the face. `TransientVisuals.ownAnchor` decides from the viewer's eye distance to the cue whether it is theirs (the cue carries no entity), and what that changes is applied only while the camera is first person, **asked every frame**: decided once on arrival, a circle cast in third person kept its full size when the camera went back and covered the whole view. The viewer's own `EYE_FORWARD` circle is a sigil at an absolute radius under an eighth of the frame at every tier (`OWN_SIGIL_BASE`, `OWN_SIGIL_PER_TIER` - the view is only 0.9 of a block tall where that circle hangs), moved off the line of sight to the hand's corner by `OWN_SIGIL_RIGHT`/`OWN_SIGIL_DOWN` of its distance (`theCasterOwnSigilNeverCoversTheCrosshair`); a ground circle is a dimmed ring at the feet; the muzzle flash is a spark at the hand (`ownMuzzleRadius`); a `SLAM` release lays its flash on the floor under the hand (`HAND_REACH`, `HAND_DROP`, `EYE_HEIGHT`), where it used to be a white sheet 0.2 of a block under every slammer's eye; and the release throws half its matter `OWN_RELEASE_PUSH` blocks further along the aim with no shader burst - thrown at the hand it was a mouthful of particles on the caster's own crosshair, and thrown nowhere the cast lost its read of leaving the hand. The legacy forward casting circle (`MagicCastingService.spawnCastingCircle`, a `MagicCircleEffectEntity` for every cast outside the Authority layer) carries its caster's id (`heldBy`, synced) and `MagicCircleRenderer` draws it for that caster in first person as the same sigil at the hand - at the two to three blocks it is written at, 1.35 blocks from the eyes, it was a wall of rings over the whole frame on every cast. **Nothing of the matter layer is on the lens**: no particle is born within `SPRITE_NEAR_CAMERA` of a first-person camera, a tinted sprite that drifts that near removes itself, and the vanilla particles thrown within `LENS_WATCH` of it are kept in a capped list and swept each tick (`SpellAccents.sweepLens`, cleared when the level changes, because a new level empties the particle engine without removing anything). A skill's own `sendParticles` is outside all of that and has to keep out of the caster's eyes by itself. Everybody else still sees all of it whole. A heavy hit (tier 3+, or scale 1.5+) blows up with vanilla's explosion sprite and a ring of puffs, but **once per spot a second** (`AccentPlan.blastEchoes`, a sixteen-entry ledger in `SpellAccents.admitBlast`), because every tier-three hit is heavy and a skill that bites one body every ten ticks stacked a blast on every beat; never within `OWN_BLAST_REACH` of a first-person camera, where the sprite is the whole view; and not at all for a surge of water, a shatter of ice or a fold of space, which ring as what they are.

### HUD

`client/hud/` — the in-game overlay. The corner block (still "the sigil" in code: `SigilRenderer`, the `magical:sigil` layer) is **Keyline**, three bands read top to bottom and nothing else: the **pools** (a mana bar over a thinner barrier bar, and beside them the counts - the mana as `82/100`, current white and maximum muted, the slash held still by `HudLayout.planPools` whatever the value reads, the current in the trouble red under a fifth, then the barrier in its bar's cyan; where the room to vanilla's centre column runs short the maximum goes first and then the barrier moves to the line beside the slots, never off the screen, and where even that will not fit the block gives up scale rather than reach in), the **slots** (the four equipped skills as bare 16px glyphs in Z X C V order with the key under each; a cooling glyph is greyed from the bottom the way vanilla greys an item on cooldown - solid grey over its shadow, not faded, because a faded glyph over a night sky is gone, and counted over the rows its ink covers rather than its square (`FxTextures.inkRows`, `SigilRenderer.inkPhase`), so a bar drawn across the middle is grey for the whole of its cooldown and not only while the line crosses it - and its key gives way to the seconds, a charging one fills from the bottom, though never while it cools: a hold input counts a held key whether or not the skill can fire) and the **readouts**, tokens flowed onto at most three lines by `HudLayout.flow`, each only while it applies. A token is a 9px **stamp** - a skill glyph at nine units, drawn whole in its owner's hue - then its words. The stamp says whose and the number says how much: it used to fill from the bottom with its gauge, and a gauge counted in the seven rows of a nine-unit mark lit one pixel at 9%, dimmed a single row at 60% and on some glyphs lit rows that carry no ink at all. Every reading names itself in its hue with its number in white. The resources - swords, vessel, corruption, notice, arcane, charge - come first; the **passives** start a line of their own: the Greed vault, `Vault 1.2k hoard 40`, whenever the sin is owned or the Vault of Avarice is on the bar, then each lit sin, `Pride 9%`. The passives are written out in full where the whole group fits and all cut to stamp and number (`9%`, and the vault without its hoard) where it does not - never a mix on one line (`HudState.placesEvery`). While a passive shows the resources get every line but the last, and anything left off is counted in a muted `+n` rather than dropped in silence; `+` means nothing else. `HudLayout.flow` returns the input index of every token it placed (`Flow.sources`), because a resource left off does not leave off the passives after it, so the places are not a prefix of the readings and a reader that paired them by position printed a resource in a sin's place. A line runs to vanilla's centre column (`HudLayout.readoutWidth`, 143 to 220), and the arcane preset's name is cut to 64, which leaves its reading well inside the narrowest line. Hue says whose, white says how much, muted says out of what, and `HudPalette.TROUBLE` - the blood accent lifted just far enough to read - says trouble; every hue goes through `HudPalette.ink`, the smallest lift toward white that reads as well as the HUD's muted text over any ground, so Wrath stays red where `textTint` would make it salmon. It was a 148px `MagicalGuiStyle.panel` whose caption was drawn with no truncation at all, so thirty-four characters of "Scroll to choose, release to switch" ran out through its own right wall onto the sky. **Frameless does not mean bare text on the world: it means a scrim.** A drop shadow preserves the shape of a glyph and does nothing for its contrast, and the numbers are brutal - measured against real noon sand (220,209,165), `TEXT_PRIMARY` lands at **1.45:1** and `TEXT_MUTED` at **2.06:1**, so the highlighted row reads *fainter* than the rows it is picked out from and the highlight inverts. Every frameless surface in the mod already dims the world for this reason (`SpaceManipulationOverlay` 0xA6, `FractureOverlay` 0x76); the switcher does it at 0x8C, which takes the same sand to (71,86,89) and the three inks to 7.23 / 5.44 / 4.71:1, in the right order. Three readings share the rail and each owns an independent channel so they cannot be confused: where the wheel points is **position and brightness** (a `>` in the gutter, the only white text on screen), what is worn is **hue** (gold, with a hairline under the name), and whether a release will do anything is the **accent colour** of that mark plus one word on a line that is reserved whether or not it is used - a cast can lock the swap while the list is open, because the cast keys still fire while B is held. The pips lead the row rather than trail it, because a trailing run needs a right edge and the right edge was the frame; an empty slot is a dash rather than a dark dot, so it differs by shape and not only by tone. `LoadoutSwitcherLayout.textLimit` is a function of `guiWidth` rather than a constant, the way both other frameless layouts clamp theirs, and `nothingReachesTheCrosshair` is the old caption bug pointed the other way. Rules:
- **Layers, not a render event.** `HudLayers` registers `magical:first_person` / `sigil` / `rule_flash` / `encounter` / `selector` on `RegisterGuiLayersEvent`; the sigil layer also calls the original combo and counter renderers, the selector layer the original hold overlays. Modded layers are not gated by `hideGui` (`Gui.java:265` wraps only vanilla's groups); `HudLayers.gated` does it.
- **Tick builds, render reads.** `HudState.tick` (end of `Hud.onClientTick`, both branches) rebuilds an immutable `HudSnapshot` only when a version changed (`ClientMagicState`, `ClientCooldowns`, `ClientStatusState`, the sword array, the sins' linger, keybinds, window, language, options). Renderers are pure functions of the snapshot + partial tick: no allocation, no `PlayerMagicState` calls, no registry lookups. Moving values are `HudTween`s; the only per-tick string is a cooling slot's seconds, reshaped when the second changes.
- **One batch.** Everything is a quad on `MagicalFxRenderTypes.hudSigil()` (`rendertype_hud_sigil.fsh`, six kinds mirrored in `HudKind`: `SLOT` (the glyphs, and at nine units with phase 0 the readout stamps) and `BAR` for the corner block, fenced in the shader with no clock in them, `CHIP` for the statuses, `PLATE` and `RULE_MARK` for the rule flash, `EMBLEM` for the codex and creator) emitted through `HudBatch` inside one `drawSpecial`; text goes after it through `HudText` with vanilla's drop shadow. Never `GuiGraphics.fill` under `client/hud` — a test forbids it. `HudSnapshotBudgetTest` pins the quad count: idle is two bars and a glyph per equipped slot, nothing a slot does costs another, and a reading costs exactly its stamp.
- **Geometry in `HudLayout`, colours in `HudPalette`, glyphs in `HudGlyphs`.** `HudLayoutTest` sweeps every anchor × scale × state for overlap and fit at 480×270, keeps the bands where they are whatever else is showing, and checks the block clears the loadout rail at the top corners - at the design scale even on a 240-tall GUI, where its third readout line ends on the row the rail's first mark starts on, which is why the gaps between the bands are 3 and never grow; at a bottom corner it cannot, so the block steps aside while the rail is drawn (`MagicWheelOverlay.isVisible`, the fade out included). A skill's glyph is its cast circle's emblem; statuses are stamps.
- **Cooldowns** are not in the state blob; `CooldownSyncPayload` (dirty-set flushed from `PlayerMagicState.sync`/`tickServer`, full list on login/respawn/dimension change) feeds `ClientCooldowns`, which extrapolates. The original wheels read it too.
- **Options** in `MagicalClientConfig` (`config/magical-client.toml`): anchor, scale, opacity, sins, statuses, compact, reducedMotion, hudDebug. `/magical hud …` forces every HUD state (sins, charge, gluttony, corruption, vessel, status, cooldown, equip, race); `-PautoHold` captures a hold overlay.
- **The rule flash** (`magical:rule_flash` layer, `RuleFlash` + `RuleFlashRenderer`): when `SpaceAuthorityService.applyRule` accepts a Manipulate Space rule it sends `SpaceRuleAppliedPayload` to the caster, and the client pops the category's formula (`magic/SpaceRuleNotation`, one bracketed symbol per category) above the crosshair for 48 ticks with the symbol tinted and moved by the operation's `SpaceRuleChange` (RAISE / LOWER / ZERO / FLIP / LOCK / SURGE / AIM / RESTORE), one `RULE_MARK` quad playing the kind's mark behind it, a caption, a faint `fp_overlay` wash, and two synthesized cues (`assets/magical/sounds/rule/*.ogg`, from `scripts/synth-rule-cues.py`; `MagicalSounds.cue`). Three quads and at most five strings, only while live (`RuleFlashBudgetTest`); nothing when idle; `reducedMotion` shortens it to 32 ticks with static marks and no wash. `/magical hud rule <category> <operation> [target]` fires one without a subspace: `.\gradlew runClient -PquickPlay="New World" -PautoCommands="magical hud rule gravity increase_gravity everything" -PautoScreenshot=52`.

### Magic Codex screen

The pyramid's rows are keyed by a skill's `tier`, and a row draws one list, so **two schools may never share a tier**: the second one is unlocked, castable and invisible. Below the line one layer is one school - -1 Blood, -2 Dark, -3 Chaos, -4 Primordial, -5 Eldritch, each named by `tier.magical.below.<layer>` - and the Authority family sits alone on `MagicPyramidMenu.AUTHORITY_TIER` (-6) below all of them, drawn from `MagicContent.authoritySkills()` rather than from its tier. `MagicContent.minTier()`/`maxTier()` count only skills with a row of their own (no authority, no sub-skills). `PyramidLayersTest` pins all of it.

`client/screen/MagicPyramidScreen` (its menu, `magic/menu/MagicPyramidMenu`, carries only button ids and data slots) wears the same frame as the creator: `client/screen/ScreenChrome` owns the 444x340 panel, the top strip (title, chip, XP bar, corner button), the hairline, the tab row and the body panel, and paints them for both screens. Four tabs - Skills (the pyramid, the owned-skill emblem rows, the active loadout's four key cards, the skill detail with its tuning), Loadouts, Passives, Classes - replace the old Back-button sub-views. **A key card takes two presses** (`MagicPyramidMenu.cardPressOpensSkill`, which the menu and the screen both ask so the client cannot guess a different answer a tick early): the first moves the cursor onto the key and nothing else, the second, on the key the cursor is already on, selects the skill bound there - which flips the pyramid, scrolls the list and fills the detail. One press used to do both, so reaching for the key you were about to bind a picked skill onto threw the picked skill away. The backdrop behind the whole frame is `MagicalGuiStyle.BACKDROP`, one 64px tile repeated by handing `blit` the tile size as the texture size and the panel size as the drawn size (u and v run past 1 and the sampler wraps, exactly as vanilla lays its own menu background; a GUI texture clamps only when its mcmeta says so and this one has none), with the old fall-off kept as a gradient over it rather than baked in. `ScreenBackdropTextureTest` pins the tile to the size the code repeats it at and holds its wrap seam to the worst seam it already carries inside itself, because a tile that does not meet itself paints a grid across the panel and nothing fails. Every rectangle is in `CodexLayout`, and `CodexLayoutTest` pins per tab that nothing overlaps, everything sits in the body, and each hit-test answers to its centre and to nothing in the gaps. Emblems come from `client/screen/EmblemPainter` (shared with the creator) in one `drawSpecial` before the tooltips. `-PautoClick="tick:x,y;..."` moves the pointer onto each point and presses the open screen for captures - it asks for window focus first, because GLFW drops a cursor move on an unfocused window without a word and an unattended capture runs unfocused, so a hover state or a tooltip can be captured too - and the codex is `HudDebug.Captured`, so one launch walks the tabs: `.\gradlew runClient -PquickPlay="New World" -PwindowSize=1280x720 -PautoCommands="magical unlockall;101:magical codex" -PautoClick="118:247,45;132:339,45;146:431,45" -PautoScreenshot=112,126,140,154 -PautoExit`.

### Spell Creator screen

`client/screen/creator/` - the workshop where the Spell Creator / Magic Originator fuses two owned skills into a third. A plain `Screen` with no container menu behind it (no inventory, no button ids): `SpellCreatorLayout` is pure geometry pinned by `SpellCreatorLayoutTest` (nothing overlaps, every hit-test is a function of the same numbers); `SpellCreatorScreen` paints chrome, then every skill emblem in one `drawSpecial` through `EmblemPainter` (the HUD sigil atlas: `HudGlyphs.skillCell` + `HudPalette.cardTint`), then text; `FormulaListPanel` is the Formulas tab. Status comes from `MagicFusionService.status` / `formulas` (`READY`, `MISSING` inputs, `LOCKED` by class, `CREATED`; sorted in that order, stable by recipe). Opened by `OpenSpellCreatorPayload` (sent by `ClassTreeMenu` and `/magical creator [formulas | create <first> <second>]`) or straight from the codex Classes tab; the one thing it sends is `CreateSkillPayload` -> `MagicFusionService.create` (`/magical create <first> <second>` is the same call, for captures). Back sends the codex request. `/magical reset` wipes the magic state for a fresh start. `isPauseScreen` is false so the integrated server answers Create; it implements `HudDebug.Captured` so the auto-closer leaves it up: `.\gradlew runClient -PquickPlay="New World" -PwindowSize=1280x720 -PautoCommands="magical reset;magical class unlock spell_creator;magical unlockall;101:magical creator create wildfire abyssal_discharge;121:magical create wildfire abyssal_discharge;141:magical creator formulas" -PautoScreenshot=112,128,152 -PautoExit`.

### Adding a new skill

1. `MagicContent` — add `register(...)` line; add id to relevant classifier set (`SUB_SKILLS`, `AUTHORITY_SKILLS`, `CLASS_REWARD_SKILLS`).
2. `MagicCastingService.castResolved` — add behavior (id branch in `if`-ladder, or generic type-based cast).
3. New entity → `entity/` class + `registry/MagicalEntities` + renderer in `client/renderer/` + bind in `MagicalClientEvents.registerRenderers`.
4. Hold/charge/multi-mode → payload in `network/` + handler in `MagicalNetwork` + client input handler wired in `MagicalClientEvents.Hud.onClientTick`.
5. Lang keys in `assets/magical/lang/en_us.json` (`skill.magical.<path>` + `.desc`).
6. Class grant lists in `MagicalClasses` if class-rewarded. Passives in `MagicPassiveContent` if passive-gated.
7. The HUD needs nothing: its slot glyph is the cast circle's emblem from the visual profile, and the cooldown greying and seconds are automatic. Only a skill with no emblem needs a stamp in `client/hud/HudGlyphs`.

Arcane content goes in `arcane/ArcaneContent` (rune/shape/modifier records) — separate flow, not the `magic/` system.
