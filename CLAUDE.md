# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"The Iceberg of Magic" — a NeoForge mod for Minecraft **1.21.4** (NeoForge 21.4.157, Java 21). Mod id: `magical`, base package `com.efkrdnz.magical`. Design intent in `Iceberg_of_Magic_Design_Document.md` (tiered magic: Arcane → Elemental → hidden Authority endgame) and `SKILL_CREATION_NOTES.md` (visual contract: no reused vanilla projectiles, custom renderers + shaders).

## Commands

```powershell
.\gradlew build                      # compile + assemble mod jar
.\gradlew runClient                  # dev Minecraft client
.\gradlew runClient -PquickPlay="New World" -PautoScreenshot=200   # join a world at launch; screenshot 200 ticks in
.\gradlew runClient -PquickPlay="New World" -PautoScreenshot=300 -PautoCommands="magical unlockall;magical hud equip 1 gabriel" -PautoHold=cast_slot_2   # ... after commands at tick 40, holding X for the last 60 ticks
.\gradlew runClient -PquickPlay="New World" -PautoCommands="magical hud rule gravity increase_gravity;100:magical hud rule velocity stop" -PautoScreenshot=52,112 -PautoExit   # commands at ticks 40 and 100, a capture at each, then the game closes itself
.\gradlew runServer                  # dev dedicated server (--nogui)
.\gradlew runData                    # run data generators → src/generated/resources/
.\gradlew runGameTestServer          # run registered gametests headlessly
.\gradlew test                       # JUnit 5 unit tests
.\gradlew test --tests "com.efkrdnz.magical.SomeTest"  # single test class
```

- On macOS/Linux use `./gradlew`; Gradle 9.2 needs a JDK ≤ 25 as `JAVA_HOME` (the Java 21 toolchain is auto-provisioned).
- `src/main/templates/META-INF/neoforge.mods.toml` is a template; `${mod_id}` etc. are expanded from `gradle.properties`. Edit template + `gradle.properties`, never generated `mods.toml`.
- `src/generated/resources/` is a resources source dir alongside `src/main/resources/`. Datagen output.

## Architecture

### Entry point & registration

`MagicalMod.java` (`@Mod("magical")`) wires all `DeferredRegister` holders from `registry/` onto the mod bus. Each registry class follows the same pattern:
- `registry/MagicalBlocks.java` — `DeferredRegister.Blocks`
- `registry/MagicalItems.java` — `DeferredRegister.Items` (all `BlockItem`s)
- `registry/MagicalEntities.java` — ~40 entities, almost all `MobCategory.MISC`, invisible gameplay entities
- `registry/MagicalMenus.java`, `registry/MagicalAttachments.java`, `registry/MagicalCommands.java`, `registry/MagicalChunkTickets.java`, `registry/MagicalCreativeTabs.java`, `registry/MagicalBlockEntities.java`

Game-bus handlers are `@EventBusSubscriber(modid = MODID)` annotated classes — never manual `NeoForge.EVENT_BUS.register`.

### Three magic systems

1. **Arcane (Tier 1, composable spell-crafting)** — `arcane/` package. Runes + shapes + modifiers defined in `ArcaneContent`, resolved by `ArcaneSpellResolver`, cast via `ArcaneCastingService`. Has its own `AttachmentType` (`ARCANE_DATA`), own sync payload (`ArcanePlayerDataPayload`), own client mirror (`ClientArcaneState`). Separate from `magic/`.

2. **Elemental skill-based (Tiers 0-5)** — `magic/` package. ~80+ skills defined as `MagicSkillDefinition` records in `MagicContent` (static `register(...)` calls with base stats). Skills classified into sets controlling random unlocks/GUI: `SUB_SKILLS`, `AUTHORITY_SKILLS`, `CLASS_REWARD_SKILLS`, `CREATED_SKILLS`. Negative `tier` values mean hidden/authority content, excluded from random rewards.

3. **Authority (hidden endgame)** — `magic/AuthorityContent.java` defines endgame unlocks (Space, Soul, Chronos). Gated behind the Authority dimension progression. Skills like `CREATE_SUBSPACE`, `MANIPULATE_SPACE`, `POCKET_DIMENSION`, `SOUL_VOW`.

### Cast flow (keybind → render)

1. **Client tick** — `MagicalClientEvents.Hud.onClientTick` polls `MagicalKeyMappings` (Z/X/C/V = 4 loadout slots, B = loadout switcher / counter answer, K = codex, R = barrier refill). Hold/charge skills (Barrage, Subspace, Aegis, Black Flames, etc.) are intercepted by per-skill input handlers (`MagicBarrageInput`, `SpaceAuthorityInput`, `SovereignAegisInput`, etc.) before normal cast. Normal press sends a `CastLoadoutSlotPayload`.

2. **Server dispatch** — `MagicalNetwork` routes payloads. `MagicCastingService.castResolved` checks cooldown/unlock/mana, then routes via an **`if`-ladder** (special skills first: Vault of Avarice, Subspace, Space Walker, Aegis, etc.), then a `switch` on `MagicSkillType` (`PROJECTILE`/`BURST`/`BARRIER`). That `if`-ladder is the real routing table — every skill with custom behavior has an explicit ID check.

3. **Entity + renderer** — Service spawns a custom entity from `MagicalEntities`. The renderer (bound in `MagicalClientEvents.registerRenderers`) draws it using custom quads/beams/rings via `MagicalRenderTypes`.

### Player data & sync

- Two `AttachmentType`s, both `.copyOnDeath()`, registered in `MagicalAttachments`: `MAGIC_STATE` (`PlayerMagicState`) and `ARCANE_DATA` (`ArcanePlayerData`).
- Sync is copy-based and wholesale: `state.sync(player)` → `PlayerMagicStatePayload` → client; `MagicalNetwork.syncArcaneData(player, data)` → `ArcanePlayerDataPayload`.
- Static client singletons (`ClientMagicState`, `ClientArcaneState`) replace their contents on payload receipt.
- Side safety: `MagicalNetwork.handleClientPayload` uses `FMLEnvironment.dist.isClient()` + reflection into `client/ClientPayloadHandlers` — server never classloads client code.

### Network

All payload records in `network/` (24 payloads). `MagicalNetwork` registers them in `registerPayloads` using `event.registrar("1")`. Play-to-client: state sync, first-person effects, counter prompts. Play-to-server: cast requests, hold/charge state, wheel casts, class actions, space rule applications.

### Classes

`classes/MagicalClasses.java` — 16 classes (Blacksmith → Divinesmith, Warrior → Berserker/Warden, etc.) as `MagicalClassDefinition` records with parent class, XP cost, granted skill IDs. Tree-based progression tracked in `MagicalClassProgress`. `PlayerMagicState.evolveClass` validates prerequisites and grants skills.

### Passives & curses

`magic/MagicPassiveContent.java` — 8 normal passives (Mana Skin, Heat/Poison/Magic Resistance, Mana Flight, etc.) + 7 sin passives + 7 curses + 1 mana leak curse. Normal passives have a disable checkbox. Curses have no checkbox — require a Dispel action with conditions. Passives appear in a separate tab in the Magic Codex.

### Space authority laws

Manipulate Space writes one law per category onto the caster's `SpaceSubspaceEntity`, whose tick runs all twelve over everything inside the radius. **A law has two halves and they run on different machines** (`magic/SpaceLawPass`): the server carries the *consequences* — damage, effects, air, the flight Control Gravity hands out, the body a boundary moves — and each *client* carries the *movement*, against its own player and nobody else's (`client/SpaceLawClient`, on `PlayerTickEvent.Pre`, so a law sets the velocity the player's input then works against). The server never writes a player's velocity because it cannot deliver one: vanilla sends the `hasImpulse` motion packet over `broadcast`, and `ChunkMap.TrackedEntity.updatePlayer` never puts a player in its own audience; the one channel that would reach them, `hurtMarked`, replaces the client's velocity with the server's copy, and nothing in `handleMovePlayer` ever writes a real one. So a law aimed at Everything or Players used to move mobs and do nothing at all to a player — every law except Control Gravity, which works only because abilities have their own packet. Adding a law means threading `SpaceLawPass` through it and putting the `setDeltaMovement` behind `pass.moves()`; `SpaceLawGameTests` fails the moment the server starts pushing players again. Captures: `/magical subspace create [radius] [follow]` raises a domain with none of the skill's gates and `/magical subspace rule <category> <operation> [target]` writes a law onto it (defaulting to `everything`), so one launch drives the real rule loop: `.\gradlew runClient -PquickPlay="New World" -PautoCommands="magical subspace create 8 true;60:magical subspace rule gravity remove_gravity everything" -PautoScreenshot=70,100 -PautoExit`. `/magical hud rule` is a different thing — only the flash, no subspace.

**The boundary** (`client/renderer/SpaceSubspaceRenderer`, geometry in `client/renderer/space/SubspaceVault`, optics in `SubspaceOptics`) is a **vault**, and the whole of it is a reaction to where the camera stands. A domain is a sphere pinned to its caster body centre (`DomainEntity` sets `owner.getY() + bbHeight*0.5`) while the camera is at their eyes, so the eye sits **0.72 blocks above the centre and nowhere else** - the horizontal offset is exactly zero - and two things follow that the dome before this fell foul of. **First, every sight line runs along the surface normal**, to within 1.43 degrees at radius 16, so the inverted Fresnel that wall was built on varied by `5.3e-10` of alpha across the entire visible sphere: a dither of 1/510 was three million times larger, and the only spatial structure on the wall was the noise. It was a flat 7% that moved a daylight sky by 15 levels and blackstone by **2 of 255**, and four green tests certified it, because every one of them measured the mean alpha over the projected disc - a property of a viewer standing *outside*, which is a viewer who cannot exist, because a domain discards itself when its owner leaves it. **Second, every meridian plane contains that eye**, and a planar curve seen from a point in its own plane projects to an exactly straight line - not nearly, exactly, at every radius and bearing. So a member drawn up a meridian is drawn as a ruler, and a straight near-vertical bar at twenty blocks is a tree trunk, a fence post or a portal jamb.

So visibility is not carried by shading at all, and the structure is not a graticule. The pane is `A_PANE` = **3%**, half what it was, a tint that carries no reading; everything legible is a **chamfer** - a lip darkening toward `BODY` meeting a lip lightening toward `GLAZE` at a one-pixel arris. The two move a background in opposite directions, so whichever lip the background defeats the other one carries, and the worst case over every background in the game has a closed form, `A_SHADOW*A_HIGHLIGHT*(GLAZE-BODY)/(A_SHADOW+A_HIGHLIGHT)` = **57 levels of 255**, which is `SubspaceOptics.chamferFloor` and is pinned by `SubspaceVaultTest.theWallCannotBeInvisible` - the test the old wall got 2 on. The arris is measured in the same `fwidth` the stroke is, so at grazing incidence both blow up together and the chamfer can never flatten into one mid-blue line. The Fresnel is kept on exactly one branch, the outside one, where `b/R` genuinely sweeps the disc and the limb genuinely is where a silhouette lives; the caster branch is fenced between two named comments and `SubspaceShaderAssetsTest.theInsideMembraneHasNoViewAngle` fails if `dot(`, `viewDir` or `shellNormal` ever appears between them.

The object: a **springing course** right round the wall, twelve **ribs** climbing from it to an open **oculus** at latitude 78 where the pane is cut away entirely, and a **plinth** tracing where the wall meets the floor. **The ribs are wound**, `bearing = 30k + twist*(latitude - springing)`, and `twist = TWIST_BASE + TWIST_PER_LAW * lawCount` - so a rib leans 23 degrees off vertical with nothing written and 52 with all twelve, and **how much law is in force is legible from the silhouette** before a glyph is parsed. That single constant answers three things at once: it takes the ribs off their meridians so they are not bars, it destroys the lat/long generator so the wall is not a wireframe globe, and it makes the shape a function of the contents. Slot *k* is `SpaceRuleCategory.values()[k]` and owns bearing 30k for good, gravity due north, so **twelve ribs wrap the whole horizon** and `floor(102.4/30) = 3` of them are in frame from every bearing there is - the reading the old band failed hardest, with all twelve marks on one arc round north and under 0.3% of the frame from three quarters of all directions. A written law makes its rib heavier (`RIB_LIT_GAIN`), colours both lips with `HudPalette.change`, lights a **notch** on the course and hangs a **boss** carrying its `SpaceRuleChange` glyph; an unwritten one is held back to `NOTCH_DIM` instead of left out, so the count has a denominator. Gravity reads twice: level is one course, inverted winds the domain the other way and lights every member from beneath, dissolved breaks the course and the plinth into dashes. Nothing has a clock - `GameTime` is forbidden in all three shader files and a test enforces it - and the only motion is three CPU one-shots: a rib climbing once as its law is written, a ring running out from a crossing, the wall fading up over 12 ticks. The springing course is placed at a constant **apparent elevation** (14 degrees) rather than a latitude, because a fixed latitude sinks underground as the radius grows; the aiming line and everything within 4 degrees of it is clear pane, which `SubspaceVaultTest.theAimingLineIsClear` holds at every radius the skill can raise.

Captures: a domain ends when its caster leaves it, so **the outside case cannot be photographed in single player** and lives in the optics test instead. Laws written at `everything` physically shove the caster off the centre of their own dome and every frame is then shot off-axis - use `everything_except_user`. The target names are `everything_except_user`, `everything`, `living_entities`, `projectiles`, `players`; there is no `mobs`. The dev world persists between runs so the stage is absolute, and `forceload add` plus twenty ticks is needed before any `fill`, or the commands run on unloaded chunks. ### Chaos authority: the Pile and the Fracture

Layer -6 with the other authorities, and the one that owns no region, no entity and no grammar. **Chaos owns a Pile in the world and a Fracture in the hand.** The Pile (`magic/chaos/Pile`) is a sparse map of *sites* to one integer of **stress**; a site is a block position or a living body (`PileSite`), its **capacity** is decided by what it is and never by who owns it (`ChaosCapacity`: stone-like 4, dirt/sand/wood 2 - named by `BlockTags` rather than measured, because cobblestone and planks are both hardness 2.0 and stone is 1.5 - glass and leaves 1, unbreakable 8, a body 2 + armour/5, a player 3, **another Authority's construct 1**, which is the counter ring expressed as a physical property). A site holding more than its capacity **gives way** into its neighbours, and a neighbour that was already full gives way in turn. The wielder is a site like anything else: there is no except-the-caster clause, because the Pile is matter and matter does not know who made it.

**There is no random number in the whole Authority.** Self-organized criticality is the canonical model of a system that is completely deterministic and completely unpredictable, which is the actual definition of chaos, so the unpredictability is a property of the arithmetic. It is also why the core is pure: `Pile`, `Fracture`, `Fault`, `PileSite` and the `PileWorld` interface have no Minecraft in them at all and `PileTest` pins every rule on an exact value. `LevelPileWorld` is the only class that knows about a level, and it answers in a **stable order** - `Direction.values()` for blocks, entity id for bodies - because ties in a sandpile are broken by neighbour order and a cascade that reshuffled its neighbours would stop being deterministic.

The **Fracture** (`Fracture`, on `PlayerMagicState`, saved as a `ListTag` of five `Fault` names) is the customizable toolkit: five faults in an order, generation *n* of a cascade giving way by fault *n* and anything deeper keeping the last. So a collapse **changes character as it grows**, along a curve its owner authored - *SLUMP → SLUMP → HEAP → SHED* is a landslide that gathers, converges and detonates. The seven faults are SLUMP (all of it to the lowest neighbour), HEAP (to whichever already holds most), BLOOM (split evenly), HUNT (only to living neighbours), RECOIL (back the way it came), SHED (passes nothing on, spends it as force and harm where it stands) and ROOT (keeps it and raises its own capacity, swallowing the cascade). Seven across five positions is 16807 machines, carried on the wielder, available the day the Authority is taken.

**Entropy is the one law that knows which way time runs, so there is no CLEAR and no RESTORE**: nothing removes stress from a site. It leaves by exactly two routes - the site gives way, or the site is forgotten. The same rule settles preparation-as-a-weapon: a site that has given way goes **slack** for `Pile.SLACK_TICKS` (600) and refuses further stress, so ground you have already avalanched is dead ground and an hour of seeding cannot be re-used on the next opponent. A slack site may still *receive*, which is how RECOIL sends a cascade back into the ground it came out of without looping forever.

Four skills, three of which carry no numbers at all (`MagicCastContentKept`, `ChaosAuthorityService`): **Burden** (2 mana, 4 tick cooldown, one unit onto whatever the crosshair is on, sneak for yourself, and it is meant to be pressed dozens of times), **The Fracture** (a hold overlay, 100 tick cooldown so it cannot be re-cut inside a cascade), **The Last Grain** (4 mana, one more unit from nowhere - on ground below capacity it is a click and nothing else, and that is the skill), and **Criticality** (72 mana, 1200 tick cooldown, every capacity in the Pile drops by one for 200 ticks so everything standing lets go at once; on virgin ground it is an expensive shimmer). Their magnitude cannot be balanced by numbers because their magnitude is the work behind them.

`PileService` holds one Pile per wielder, keyed by UUID, and **it is never saved**: stress is dropped on logout and rebuilt from nothing on a change of dimension. That is thermodynamically apt and it settles griefing, the save format and unbounded growth in one decision - the kit the player authored survives, the battlefield does not. It runs the avalanche on `ServerTickEvent.Post` with a per-tick budget (`Pile.DEFAULT_BUDGET` = 48) so a long cascade visibly rolls over a second or two instead of resolving inside one frame, paints stress as `ParticleTypes.WITCH` motes every 10 ticks (**visible to everyone**, which is the whole of the counterplay: break the block it sits on, hit the body carrying it, deny the ground) and puts an `n/cap` readout on the actionbar for the aimed site. A proper crosshair pip belongs on a HUD layer through `HudBatch` and would move `HudSnapshotBudgetTest`; deferred.

### Forged strikes (the blacksmith/divinesmith left click)

An attack press holding a `magical:forged_weapon` runs `ForgeComboService`/`ForgePayloadService` -> `ForgeStrikeEntity.spawn` -> synced data -> `client/renderer/ForgeStrikeRenderer.extractRenderState` -> `ForgeForms.render` -> one of eight geometry classes in `client/renderer/forge/` (seven share one `forgeEdge()` consumer; SLAM spans two render types and is handed the source, because `ForgeBuffers` forbids two live consumers on the shared buffer).

Seven of the eight are built from `ForgeRibbon`. An arc of blade is a **closed solid**, not a sheet: four faces per segment, a lens cross-section (`crossSection`) that is sharp at both lips and thickest on the spine, tapered along its length by `bladeProfile`, with `planar(plane, u, v, n)` putting the thickness on the one axis the plane does not span.

**A swing may lean; a thrown thing may not.** An arc has a belly and a belly points somewhere — fine for a swing, which is a thing done in a direction with the wielder standing at the middle of it, and wrong for the wave, where whichever direction gets picked is arbitrary *and* is not the direction the wave is travelling. The wave was drawn tipped up-right, then bowed belly-down, and both were the same mistake. So it is not an arc at all: `ForgeWaveFront` is a **surface of revolution about the aim** — `point(radius, depth, angle, across)` gives the angle no say in depth, so the middle leads, the rim trails, and the sheet is identical at every roll angle about the flight line. `WaveSilhouetteTest` pins exactly that, plus the sizing below. Rings bunch toward the rim (`RIM_BUNCH`) so the shader's cutting lip lands on a thin band and the front ends on an edge; `halo` is its rim glow, written there rather than borrowed from `sheath` because a sheath tapers to nothing at both ends of its arc and a ring has no ends — a seam would be an in-plane direction again. Its wake is short and tapers hard (`TRAIL_GAP`, `TRAIL_SHRINK`): the thrower stands *behind* a wave, so every trail copy is nearer the camera than the head and perspective alone draws it larger.

**A drawn form must sit on the volume that actually hits.** An arc is measured from the centre of its own circle, so a crescent built at radius R puts every one of its pixels R blocks from the strike and none of them on it — which is how the wave came to be a band hanging between 1.5 and 3 blocks off the flight path, rolled 40 degrees, claiming nearly four times the width it catches in. `WaveSilhouetteTest` measures the drawn sheet against `HitShapes.forFamily(WAVE).broadInflation(halfWidth, reach)` — `WaveShape` inflates the swept box by `halfWidth * 0.48` laterally and a flat `0.9` vertically, and its `hits` only rejects things behind the wave, so that box *is* the hit volume. The vertical `0.9` does not grow with the weapon, so `WaveGeometry.radius` is a `min`, not a fraction: a heavy divine blade would otherwise be drawn reaching half again as far up and down as it catches. The glow and the wake are deliberately outside the measurement: a glow is light, and a wake is where the blade has already been, which the swept box covers. `ForgeMotion` opens an arc along its own span (`opening`) or grows a thrown one out to its reach (`reaching`, and `reached` for the factor alone, so the wave's front and the ring of ornaments round its rim cannot drift apart) - both capped so the drawing never claims more than the hit shape. Three things then sit on top of the steel, and all three exist because of one complaint - a swing seen down the line of its own plane is close to a line, and a picture of nothing but smooth ribbons reads as fog:
- **`ForgeAura`** - the one call each form makes after its arc. It reads the viewer's position straight off the pose matrix (`ForgeView.eye`, the inverse applied to the camera-relative origin), so a form that lifts, tilts, rolls or fans its arc is accounted for without saying so.
- **`ForgeRibbon.sheath` / `lanceSheath`** - a camera-facing glow band along the blade's spine. Its v runs 0.5 at the centreline to 0 at both rims, so it is symmetric and the shader's cutting-lip term never fires on it. Drawn once per strike, not once per trail copy.
- **`ForgeSparks`** - debris off the cutting lip, hashed from the entity id so every client sees the same shower. Slim camera-facing streaks; `count` is the grade's.

`rendertype_forge_edge.fsh` is where a strike gets its colour. The render type blends **`ONE, ONE`** - the alpha channel is discarded outright - so the vertex alpha must be folded into rgb, exactly as `magic_common.glsl`'s `additiveOut` does; `CEILING` is set from the layer stack (two faces x four to six trail copies ~ 3.5x) so the hottest pixel lands near white and everything short of it keeps the element's hue. `core` is the one term with a hard boundary and is deliberately kept out of the noise.

The weapon's own numbers show: element owns colour and ornament (`ForgeElementAccent`), form owns the silhouette, temper and modifiers already move `halfWidth`/`reach` through `ForgeStrikeMath`, and **`ForgeWeaponLook`** adds the last two - grade scales emission 0.62..1.28 and spark count 3..18, quality scales blade breadth 0.86..1.18 - applied once in the renderer, off `state.alpha` and `state.halfWidth`, so all eight forms inherit them.

Captures: a strike is born from a left click, and `-PautoClick` only reaches an open screen while `-PautoHold` only reaches a registered key mapping, so neither can press attack. `forge/ForgeStrikeBench` spawns one through the real `ForgeStrikeMath.resolve` and `ForgeStrikeEntity.spawn`: `magical-debug forge strike <form> <element> [class] [grade] [heavy]` for one, `magical-debug forge bench <element> [class] [grade] [heavy]` for one of every family at once (`heavy` is a literal, not a boolean). Judge colour at **midnight** - additive over daylight sand clips to white by construction, which every glowing effect in the mod shares - and judge shape in **first person**, which is how it is played and the angle every arc is most nearly edge-on at. The wave is the exception and needs a second camera off the flight line — a dome and a flat disc are the same picture seen down their own axis, so face-on says nothing about whether it curves; throw it facing `0 0`, then `tp @s ~-4 ~1 ~-9 -20 25` a tick or two later for the three-quarter view that shows the cup. Forms live 3 to 6 ticks (a wave 20), so a screenshot lands one or two ticks after the spawn: `.\gradlew runClient -PquickPlay="New World" -PwindowSize=1280x720 -PautoCommands="gamerule sendCommandFeedback false;magical reset;magical hud race human;magical class unlock blacksmith;time set midnight;tp @s ~ ~ ~ 0 0;140:magical-debug forge strike magical:slash magical:fire sword divine;150:magical-debug forge strike magical:cleave magical:fire sword divine;160:magical-debug forge strike magical:thrust magical:frost sword divine;170:magical-debug forge strike magical:spin magical:fire sword divine;180:magical-debug forge strike magical:slam magical:fire sword divine;190:magical-debug forge strike magical:wave magical:void sword divine;215:magical-debug forge strike magical:rising magical:fire sword divine;225:magical-debug forge strike magical:flurry magical:fire sword divine" -PautoScreenshot=141,151,161,171,181,193,216,227 -PautoExit`; add `-PautoCamera=third_back` for the same run seen from outside.

### HUD

`client/hud/` — the in-game overlay, "the sigil": concentric ring meters (XP, mana, barrier, the charge halo) round a core that carries the numerals (level, mana, barrier, vault), a crown of sin satellites, a fan of cast cards on spokes with key tags and a seconds numeral while cooling, text readouts for the lit sins beyond the tags, captions under the fan, a reflection of the pools under a waterline for blood/dark mages, status chips under the crosshair, and announcements of what the player just gained. The hold overlays (sub-skill wheels, space dials, switcher, blood strip), the counter box and the combo readout are the original `GuiGraphics` code, untouched. Rules:
- **Layers, not a render event.** `HudLayers` registers `magical:first_person` / `sigil` / `rule_flash` / `encounter` / `selector` on `RegisterGuiLayersEvent`; the sigil layer also calls the original combo and counter renderers, the selector layer the original hold overlays. Modded layers are not gated by `hideGui` (`Gui.java:265` wraps only vanilla's groups); `HudLayers.gated` does it.
- **Tick builds, render reads.** `HudState.tick` (end of `Hud.onClientTick`, both branches) rebuilds an immutable `HudSnapshot` only when a version changed (`ClientMagicState`, `ClientCooldowns`, `ClientStatusState`, `HudAnnouncer`, keybinds, window, language, options). Renderers are pure functions of the snapshot + partial tick: no allocation, no `PlayerMagicState` calls, no registry lookups. Moving values are `HudTween`s; the only per-tick string is a cooling card's seconds, reshaped when the second changes.
- **One batch.** Everything is a quad on `MagicalFxRenderTypes.hudSigil()` (`rendertype_hud_sigil.fsh`, eleven kinds mirrored in `HudKind`) emitted through `HudBatch` inside one `drawSpecial`; text goes after it through `HudText` with vanilla's drop shadow. Never `GuiGraphics.fill` under `client/hud` — a test forbids it. `HudSnapshotBudgetTest` pins the quad count.
- **Geometry in `HudLayout`, colours in `HudPalette`, glyphs in `HudGlyphs`.** `HudLayoutTest` sweeps every anchor × scale × state for overlap and fit at 480×270, and checks the core holds its numerals. A skill's icon is its cast circle's emblem; sins and statuses are stamps.
- **Cooldowns** are not in the state blob; `CooldownSyncPayload` (dirty-set flushed from `PlayerMagicState.sync`/`tickServer`, full list on login/respawn/dimension change) feeds `ClientCooldowns`, which extrapolates. The original wheels read it too.
- **Options** in `MagicalClientConfig` (`config/magical-client.toml`): anchor, scale, opacity, sins, statuses, compact, reducedMotion, hudDebug. `/magical hud …` forces every HUD state (sins, charge, gluttony, corruption, vessel, status, cooldown, equip, race); `-PautoHold` captures a hold overlay.
- **The rule flash** (`magical:rule_flash` layer, `RuleFlash` + `RuleFlashRenderer`): when `SpaceAuthorityService.applyRule` accepts a Manipulate Space rule it sends `SpaceRuleAppliedPayload` to the caster, and the client pops the category's formula (`magic/SpaceRuleNotation`, one bracketed symbol per category) above the crosshair for 48 ticks with the symbol tinted and moved by the operation's `SpaceRuleChange` (RAISE / LOWER / ZERO / FLIP / LOCK / SURGE / AIM / RESTORE), one `RULE_MARK` quad playing the kind's mark behind it, a caption, a faint `fp_overlay` wash, and two synthesized cues (`assets/magical/sounds/rule/*.ogg`, from `scripts/synth-rule-cues.py`; `MagicalSounds.cue`). Three quads and at most five strings, only while live (`RuleFlashBudgetTest`); nothing when idle; `reducedMotion` shortens it to 32 ticks with static marks and no wash. `/magical hud rule <category> <operation> [target]` fires one without a subspace: `.\gradlew runClient -PquickPlay="New World" -PautoCommands="magical hud rule gravity increase_gravity everything" -PautoScreenshot=52`.

### Adding a new skill

1. `MagicContent` — add `register(...)` line; add id to relevant classifier set (`SUB_SKILLS`, `AUTHORITY_SKILLS`, `CLASS_REWARD_SKILLS`).
2. `MagicCastingService.castResolved` — add behavior (id branch in `if`-ladder, or generic type-based cast).
3. New entity → `entity/` class + `registry/MagicalEntities` + renderer in `client/renderer/` + bind in `MagicalClientEvents.registerRenderers`.
4. Hold/charge/multi-mode → payload in `network/` + handler in `MagicalNetwork` + client input handler wired in `MagicalClientEvents.Hud.onClientTick`.
5. Lang keys in `assets/magical/lang/en_us.json` (`skill.magical.<path>` + `.desc`).
6. Class grant lists in `MagicalClasses` if class-rewarded. Passives in `MagicPassiveContent` if passive-gated.
7. The HUD needs nothing: its card icon is the cast circle's emblem from the visual profile, and the cooldown sweep and seconds are automatic. Only a skill with no emblem needs a stamp in `client/hud/HudGlyphs`.

Arcane content goes in `arcane/ArcaneContent` (rune/shape/modifier records) — separate flow, not the `magic/` system.
